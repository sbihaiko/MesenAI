# ADR-0013: Exporter timing derives from an emulated 44100 Hz sample counter, not host clock or nominal cadence

- Status: accepted
- Date: 2026-08-24
- Related: ADR-0157 (the same emulated-frame axis, headless-input side)

## Context
Raised during decompose, Execute/T1, Execute/T2 and auditor-b (consolidates former ADR-0015, ADR-0018, ADR-0019, ADR-0023). The mandated timestamp-free signatures (`LogWrite(chip, addr, value); LogFrame(consoleTag, presetId, Input)`) forced both exporters to invent time: `VgmExporter::EmitWait` derives VGM waits from `std::chrono::steady_clock` deltas, so fast-forward, rewind, pause, save-state load, frame-limiter off or a stalled host frame write waits that do not match the music produced; `MidiExporter` derives ticks from a hardcoded nominal cadence (`FlushRateHz = 179.0`), while the real cadence is each console's `PlayAudioBuffer` rhythm (NES NTSC ~179 Hz, PAL ~149 Hz, GB/SMS their own), so a PAL capture comes out ~20% fast against the 120 BPM / 480 PPQN grid. Both break the PRD's success criteria (VGM opens in vgmrips/foobar2000, MIDI in MuseScore). A per-call masterClock argument and a registered sample-count clock source are incompatible; an audit round re-raised the axis (ADR-0024 and ADR-0030, both consolidated here), but ADR-0024's premise that MidiExporter inherits VgmExporter's std::chrono cadence is wrong against the shipped code — MidiExporter uses the fixed `FlushRateHz = 179.0` with a carried fractional remainder, so wall-clock failure modes do not distort MIDI note lengths, and its only genuine residual is the constant scale factor on PAL/GB/SMS captures. The wall-clock defect is real for the VGM side (`EmitWait`).

## Decision
Adopt the emulated-sample-counter variant: `SoundMixer` updates a 44100 Hz sample counter on the exporter, and both VGM waits and MIDI ticks derive from it. For MIDI, extend `LogFrame()` with the `sampleCount/sampleRate` every `MixAudio(out, sampleCount, sampleRate)` caller already has in hand, keeping `FlushRateHz` only as a fallback when the caller passes 0; `steady_clock` remains only as a fallback when no clock source is registered. Extract the four inlined tick-advance lines at `MidiExporter.cpp:32-36` into the `AdvanceTick()` member the header already claims exists — the swap-in seam, closing the doc/code drift in one edit (the split in ADR-0034 makes room). The per-call masterClock alternative is rejected: it means three heterogeneous clock domains (NES 1.79 MHz, GB 4.19 MHz, SMS 3.58 MHz) every write-site must convert, whereas the 44100 Hz counter is uniform across consoles, matches the VGM timebase natively, and preserves the one-liner call sites.

## Consequences
Captures become cycle-faithful, immune to fast-forward/pause/host stalls. Highest-priority fix in the audit set: the cost is six call sites now, much higher after F1.3 and the remaining console wiring, so it lands before any further wiring; it changes what a produced file means, not merely how it is produced.

## Alternatives
Rejected: a per-call masterClock argument, and keeping host wall-clock / nominal cadence (wrong tempo per region and per host condition). Keep the nominal 179 Hz cadence behind a tick-source seam and swap later (audit-round ADR-0024): superseded — the seam ships as an implementation step here, but deferring the swap leaves PAL/GB/SMS captures at the wrong tempo and the retrofit cost grows with F1.3 and the remaining console wiring.
