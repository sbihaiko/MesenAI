# ADR-0120: Last-priority subfolder fallback for MEP zip discovery

- Status: accepted
- Date: 2026-08-26
- Extends ADR-0040 (storage/discovery precedence) and ADR-0049 (sibling folder convention, zip-named-as-ROM), without reordering either.

## Context
MEP-v1 §2.1 accepts a zip pack in `EnhancementPacks/` in exactly two shapes: a `pack.json` at the zip root (ADR-0040 rule 1), or a zip whose base file name equals the ROM's name — "zip = the folder, zipped" (ADR-0049 rule 1). `MepPackManager::PrepareZip` enforces this with no recursion: it builds a normalised `(entry, path)` plan from the zip's entry list, sets `hasPackJson` only when an entry normalises to exactly `"pack.json"` (Core/Shared/EnhancementPacks/MepPackManager.cpp:399-411), and rejects the whole pack when that is false and the zip's base name does not case-insensitively equal `_romName` (MepPackManager.cpp:412-415) — no entry is inspected for a *subfolder* named after the ROM. Independently, `MepPack::DetectConventionLayout()` only probes `RootFolder/kConventionProbe[i]` and `RootFolder/auto/kConventionProbe[i]` (Core/Shared/EnhancementPacks/MepPack.cpp:53-80), never a descendant. Both facts were confirmed by reading the source during this decision.
Real community packs do not always ship this way: a release zip built by `git archive`/GitHub Releases commonly wraps its payload one level down (`<Repo>-<tag>/`, a promo/screenshots sibling, or both). Under today's rule such a zip has no root `pack.json` and its base name does not equal the ROM name, so it is rejected outright even though a valid MEP-shaped layout exists one level down.

## Decision

### 1. Additive, lowest-priority extension — not a precedence change
This ADR adds a **fourth, last-resort** rule after the three ADR-0040/ADR-0049 rules (sibling folder → `HdPacks/<Game>/` legacy → `EnhancementPacks/` containers matched by pack.json-root or zip-name-equals-ROM). It fires **only** when a zip candidate has already failed both existing zip-acceptance tests (no root `pack.json`, base name ≠ ROM name). It never changes which candidate wins when an existing rule already matches, never widens what counts as a sibling folder or a `pack.json`-rooted container, and never applies to directory packs (which have no "wrapper" ambiguity — a directory's identity is its own path). The existing precedence chain, and the "first pack per section wins" tie-break of ADR-0040 rule 4, are unchanged.

### 2. A pure, I/O-free function that `PrepareZip` consults
The subfolder search is a pure function — no `ZipReader` call, no filesystem access, no cache/extraction side effect — taking the already-normalised entry-path list `PrepareZip` builds before its accept/reject decision (the `plan` vector at MepPackManager.cpp:399-411) plus the ROM name, returning an optional discovered prefix. `PrepareZip` calls it once, only where `hasPackJson` is false and the name check failed, replacing an unconditional `return false`: no unambiguous prefix → reject exactly as before (same `error` string); one found → proceed with the normal extraction loop and combine the extraction root with the discovered prefix through `MepPack::NormalizeRelativePath` to produce `outFolder`.

**`PrepareZip`'s public contract is held fixed on purpose.** Its signature stays `bool PrepareZip(const string& zipPath, const string& cacheRoot, string& outFolder, string& error)` — no new parameter, no new output, no change to what `outFolder`/`error` mean. The fallback is internal: which prefix under the already-planned extraction becomes the pack root, so every caller keeps seeing a convention-shaped directory. It operates purely on `vector<string>` entry paths already in memory, so it is unit-testable with literal fixtures, no zip I/O, and keeps `ZipReader`/miniz out of `core-unit-tests`.

Depth and entry-cap bounds (max depth 4 path segments, max 2000 visited entries, fail-closed on overflow — treat overflow as "no candidate found", never a crash or unbounded scan) apply identically here and to the C#/Python mirrors (§3). "Depth" is the count of `/`-separated segments in the normalised entry path (e.g. `Contra80s-v1.1/Contra (U) [!]/hires.txt` is depth 3), pinned in each language's comment because the task supplies no formula and a silent divergence would make the three implementations agree on their own tests while disagreeing with each other. Ambiguity is fail-closed: more than one candidate satisfying the acceptance test reports "not found" rather than guessing, and `PrepareZip` falls through to the existing rejection.

### 3. C++ matches by name; C#/Python match by structure — an intentional asymmetry
`PrepareZip` has `_romName`, the exact ROM identity being loaded, so the C++ fallback's acceptance test is a **name match** — a single-segment subfolder whose name equals the ROM name (case-insensitive), mirroring the rule it extends. `MepZipValidator.Validate(ZipArchive)` (C#) and `mep_lint.py` (Python) run where no ROM name is available — `Validate` is called from `InstallPack` in `UI/ViewModels/EnhancementPacksViewModel.cs:121`, which opens a generic file-picker and copies the zip into the shared `PacksFolder` (`UI/ViewModels/EnhancementPacksViewModel.cs:110-133`) with no ROM in scope, and `mep_lint.py`'s CLI takes only a downloaded pack path (`argv[1]`) for `.github/workflows/community-pack-validate.yml`, not a ROM — so their fallback is **structural**: does a candidate subfolder, treated as the zip root, satisfy the existing `LayerProbes` / `PROBES`/`AUDIO_ALT_PROBE` probe test (`textures/hires.txt`, `audio/hires.txt` or `audio/fingerprints.json`, `synth/preset.cfg`)? Deliberately looser than the C++ name match (accepts any name whose contents look like a pack) and deliberately **not** loosened to "accept the first plausible candidate": more than one structurally-valid candidate is ambiguous and rejected, fail-closed as in §2.

This is an intentional, documented asymmetry. Unifying it needs the ROM name the validators lack. **Named follow-up (not this task):** add an optional ROM-name parameter to `MepZipValidator.Validate` and to `mep_lint.py`'s CLI (e.g. an optional second argument) so a caller with that context can tighten to the C++ name match. *Status update (ADR-0121, 2026-08-27):* the Python half is implemented — `scripts/mep_lint.py` accepts an optional second positional ROM name and, when the structural fallback finds nothing, tries the ROM-name-anchored `find_fallback_subfolder_by_name`; the CI workflow can supply the name from the issue form. The C# validator (`UI/Logic/MepZipValidator.cs`) remains structural-only (`FindStructuralFallbackPrefix`, no ROM-name parameter).

Deferral (2026-09-01): the C# half stays deferred. `MepZipValidator.Validate(ZipArchive)` still has one production caller, `InstallPack` in `UI/ViewModels/EnhancementPacksViewModel.cs:188`, which still copies into the shared `PacksFolder` with no ROM in scope, so a new parameter would have no caller that can supply a value — dead code only the unit tests exercise. The Python mirror also does more than the C++ exact match: `find_fallback_subfolder_by_name` (`scripts/mep_lint.py:323`) falls back to a region/flag-tag-normalised comparison via `normalize_rom_core_name`, so a faithful C# port is not contained, and an exact-only variant would introduce a third, divergent semantics. Trigger: the per-ROM install caller named above — implement the parameter in the same change, porting the normalised comparison and covering it in `UI.Tests/Mep/MepZipValidatorTests.cs`.

Re-verified 2026-09-07: the per-ROM caller now exists — the ADR-0146/0147 community auto-install runs through `CommunityPackInstallService` into the `InstallMepRecipe` ABI, which carries the ROM name — but that path validates via the **authoritative C++ `MepPackManager::PrepareZip`**, never the C# `MepZipValidator`, so a C# ROM-name parameter would still have no production caller. The deferral stands; pick it up only if a C# path appears that both knows its ROM and pre-flights the zip itself.

### 4. Deferred: a standalone C++ E2E zip-pipeline test harness (implemented 2026-09-03)
This task does **not** build a driver linking `MepPackManager.cpp` + `ZipReader.cpp` + miniz + `ArchiveReader` to exercise `PrepareZip` end-to-end against a real `.zip`. §2's pure-function extraction makes the fallback *logic* testable now via `core_unit_tests` (the no-`ZipReader` seam at `scripts/core_unit_tests.cpp` / `Makefile`'s `core-unit-tests` target) with literal `std::vector<string>` fixtures; what it cannot exercise is the surrounding I/O: real zip extraction, the `.mep-source` stamp cache-reuse branch, `NormalizeRelativePath` with a real `FolderUtilities::CombinePath` on disk, zip-slip rejection against actual archive bytes. A standalone E2E harness is a **separate follow-up** (the originating task's Scope Boundaries kept it out).

Deferral (2026-09-01): still deferred. Re-verified: `scripts/core_unit_tests.cpp` exercises only the pure `MepPack::FindFallbackSubfolder` with literal fixtures; `scripts/headless_record.cpp` is the C++ headless driver for audio/HD-pack recording, loading packs from folders in the scratch home; `scripts/verify_community_install_from_zero.py` covers the community *install* pipeline end-to-end (No-Intro sha1 → catalog match → allow-listed download → sha256 check → extraction → headless load), but extracts in Python (`extract_legacy_pack`, mirroring the C# `LegacyHdPackInstall`) into `HdPacks/<romName>/` as a folder, so the C++ `PrepareZip` zip path (real extraction, the `.mep-source` stamp cache-reuse branch at `MepPackManager.cpp:634`, zip-slip rejection on real archive bytes) is not what it proves; `scripts/mep_live_validate.py` likewise extracts to an `EnhancementPacks/<rom>/` folder first. Only `scripts/gen_mep_test_pack.py`'s `zip`/`slip` kinds put a real zip through `PrepareZip`, and that is a manual `headless_record ... log` inspection, not an asserting harness. Trigger: a regression in `PrepareZip`'s zip path the pure-function tests cannot reproduce, or the real `Contra80s.zip` inspection below being scheduled.

Implemented 2026-09-03 (wave 2 of `docs/validation/process/manual-validation-automation-plan.md`), by a seam rather than a new binary: the whole `PrepareZip` pipeline now lives in `Core/Shared/EnhancementPacks/MepZipExtract.h` — stamp/cache reuse, stale-cache wipe, zip-slip plan validation, the §2 fallback resolution and the extraction itself — and `MepPackManager::PrepareZip` delegates to it. An `IArchive` seam keeps the real archive readers (and `ZipReader.cpp` + miniz) out of the test link, so `scripts/core_unit_tests.cpp` **Bloco M** drives the pipeline with in-test archives inside the existing `core-unit-tests` target. Asserted: path traversal, an absolute path (including a Windows drive letter), the nested-wrapper fallback of §2 on a real wrapped archive, `.mep-source` cache-stamp reuse, stale-cache wipe, a symlink left in the cache being wiped, the empty-archive guard, and the `.mep-source` stamp itself. Each check was defect-probed: mutating it makes Bloco M fail. One caveat: miniz's writer cannot author a true `S_IFLNK` entry, so symlink handling is covered by its two reachable halves — an entry whose payload is a path (which writes as a plain file) and a pre-existing cache symlink — not a real symlink inside an archive.

## Provenance of the motivating claim (see also AC-8)
The pack that motivated this fallback is issue #3, "[Community Pack] Contra80s (NES)" (https://github.com/sbihaiko/MesenAI/issues/3), naming `Contra (USA)` / NES and linking `https://github.com/TasticHacks/Contra80s/releases/download/1.1/Contra80s.zip` (release `1.1`, asset `Contra80s.zip`, size ≈91MB).

**Independently verified by reading the source this session:** `MepPackManager::PrepareZip` (MepPackManager.cpp:399-415) and `MepPack::DetectConventionLayout()` (MepPack.cpp:53-80) require an exact root layout — `pack.json` (or a convention probe) must sit directly where `PrepareZip` extracts to, no recursion into any subfolder. This is independent of any claim about the real Contra80s zip.

**Not independently re-verified:** the published `Contra80s.zip`'s actual internal structure. Neither this decision session nor the implementing one opened the ~91MB asset; the "wraps its payload one level down" shape used for the test fixtures (e.g. `Contra80s-v1.1/Contra (U) [!]/hires.txt`) is the shape described in the task/issue text and in this project's memory of GitHub-Releases-style zips, not a structure confirmed by opening the archive. Any statement that "the real Contra80s pack would not load today without this fallback" is therefore a claim **qualified by that coverage gap** — deductive from the verified non-recursive requirement applied to the *described* shape, not an end-to-end observation. A future pass that runs the real `Contra80s.zip` through `PrepareZip` (or `mep_lint.py`) would close it.

## Consequences
- A zip that today gets `error = "zip has no pack.json at its root"` for wrapping its content one level down in an unambiguous, ROM-named (C++) or pack-shaped (C#/Python) subfolder now loads/validates instead of being rejected — with zero change to how any already-accepted pack is discovered or which pack wins a section.
- The fallback adds one more code path in each of three languages, bounded by the same depth/entry-cap constants (`verify_mep_fallback_constant_parity.sh` keeps them in lockstep) and the same fail-closed-on-ambiguity philosophy, though the acceptance test differs by design (§3).
- `PrepareZip` callers, `outFolder`/`error` semantics, and every other caller of `MepPack::DetectConventionLayout()` are unaffected — the fallback only decides *what* gets extracted where.
- Two follow-ups were explicitly deferred, not silently dropped: an optional ROM-name parameter for `MepZipValidator.Validate`/`mep_lint.py` (§3 — done for `mep_lint.py`, still open for the C# validator; see ADR-0121), and a standalone C++ E2E zip-pipeline harness (§4, implemented 2026-09-03 as `Core/Shared/EnhancementPacks/MepZipExtract.h` + `core_unit_tests` Bloco M).

## Alternatives
- **Recurse in `DetectConventionLayout()` itself** (search subfolders at load time): rejected — conflates "which folder is the pack root" (a discovery-time, zip-specific question) with "does this root have a convention layout" (unchanged, AC-3), and would extend `DetectConventionLayout()`'s signature.
- **Give C# and Python the ROM name now:** rejected — both call sites (installer UI, CI's `mep_lint.py` invocation) would need call-site changes, out of scope; recorded as the §3 follow-up.
- **Unbounded/recursive subfolder search:** rejected — unbounded traversal over an attacker-influenced entry list is a resource-exhaustion surface; the depth-4/entry-cap-2000 bounds close it deterministically.
- **Accept the first plausible candidate instead of rejecting on ambiguity:** rejected — silently picking one of several subfolders would make pack loading non-deterministic across a re-inspected zip whose entry order changes, and would contradict the fail-closed posture ADR-0040's zip-slip validation establishes for this path.

## Amendments (2026-09-06, code-review pass)
- `PrepareZip`'s cache-hit path returns the prefixed folder directly, using the root prefix recorded in the second line of `.mep-source` (ADR-0040 amendment). The public signature is unchanged as §2 requires; the behavioural difference is that a fallback zip is extracted once, not on every load.
