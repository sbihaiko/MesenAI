# F12.2 — retest of the 6 ROMs blocked before dispatch, after PR #352

**Date:** 2026-09-20
**Baseline:** `docs/validation/f12.2-sonnet-sweep-2026-09-19.md` (merged to
`main`), whose *Not evaluable* section names six ROMs — Bubble Bobble,
Donkey Kong, Golf, Ice Climber, Tetris, The Flintstones — that never reached
evaluator dispatch because `scripts/f122_prepare_evaluator.py`'s
`choose_frame` step hit the "no candidate second draws a single background
`<tile>` rule … the screen is drawn by a captured whole-screen `<background>`"
gate at every candidate second, tied to issues #339/#349.
**Fix under test:** PR #352 (merge commit `e67f8a9b`, already on `main` in
this worktree — no rebase was needed), implementing ADR-0217 (Option A+C)
and ADR-0218 (Option A+B): forced-rival anchor selection plus write-time and
post-hoc collision guards in `Core/NES/HdPacks/HdPackBuilder.cpp` /
`ScreenStitcher.cpp`. Both #339 and #349 are closed.
**This is an addendum, not a revision** of the original sweep doc — nothing
there was edited.

### Golf and Donkey Kong: the fix works

Both are unambiguous confirmations that PR #352 fixes the specific failure
this task set out to retest. Both recordings hit an actual gameplay-visible
background (not just an attract/title card), the fixed anchor selection
produced `<tile>` rules that draw at a real candidate second, and
`choose_frame` returned normally instead of raising `PrepareError`. Neither
of these two ever triggered the old gate.

### Ice Climber, Tetris, Flintstones: past the #339/#349 gate, into different, already-known problems

All three now get *past* `choose_frame`'s whole-screen-capture check — the
fix under test does what it was supposed to do for them, too, in the narrow
sense that the specific failure signature from the original sweep
(`PrepareError: no candidate second draws a single background <tile> rule`)
does not recur. But two different, pre-existing dispatcher defects take
over immediately after:

- **Ice Climber** hits the nametable/window ambiguity the original sweep
  already catalogued in Dr. Mario, Super Mario Bros., Zelda II and
  Gauntlet — `choose_frame` cannot place a visible-window box on the
  tilemap dump, so the evaluator has to reason from dimming alone. Per the
  task's boundary this is noted, not re-investigated.
- **Tetris** and **Flintstones** land on a frame where the pack's own
  recorded background practically does not appear on-screen (2/105 and
  0/187 keys, respectively) — the reference frame these particular
  90-second, no-input recordings picked is functionally a title/attract
  card, independent of the anchor-collision bug. This is a recording-input/
  duration limitation (a short, no-input recording of these two ROMs never
  leaves the title screen for long enough to capture real gameplay
  background art), not #339/#349, and is out of this task's scope to chase
  further. Flintstones' evaluator declined outright (nothing confirmed
  on-screen); Tetris' evaluator did find one legitimate on-screen shape (an
  outer border tile) and completed the full pipeline on it — see its result
  below, which failed for a *third*, separate, already-known reason.

### Bubble Bobble: still blocked, for a different reason than #339/#349

Two attempts, 90s and then 240s (both `bootstrap hdpack-off`, no input
script), produced identical outcomes: `choose_frame` fails with the exact
original error text, 0 background `<tile>` rules drawn at every candidate
second, from either the rebuilt pack or the recording's own `auto/` layer.

Inspecting the recorded pack explains why, and why this is not the
#339/#349 failure mode the fix addresses:

- `textures/hires.txt` has **exactly one** `<background>` entry
  (`backgrounds/screen001.png`, gated on three `tileAtPosition` anchors),
  and **zero** sheets classified `kind: "background"` among its 9 sheets
  (`adjacency`, `sprites`, `misc`, `unsorted`, `font`, `hud`, `sprite`,
  `metatiles`, one unclassified).
- ADR-0217/ADR-0218 fix what happens when **two or more** captures'
  anchor gates collide (variant-vs-rival misclassification, or two pending
  screens converging on the same triple independently). Bubble Bobble's
  pack has only one captured background — there is no collision to
  resolve, and the fix has nothing to act on here.
- This one background's gate is satisfied at every candidate second
  because a 90-240 second **idle, no-input** recording of this game never
  leaves its title/attract screen. Per `f122_prepare_evaluator.py`'s own
  docstring (written from the earlier, pre-fix sweep): "the 23 rules that
  won the frame are the attract mode's bubbles… the background layer draws
  nothing, and the logo sitting in VRAM is never fetched." A single
  captured background correctly and consistently describing "the one
  screen this idle recording ever shows" is the captured-background
  design working as intended (ADR-0050/ADR-0156: a capture owns its
  cells), not a bug in either the pre- or post-fix anchor logic.
- Unblocking this ROM would need a recording that actually reaches
  gameplay (a title-screen `T` press or similar, the way
  `reference_nes_rom_library_entry_scripts.md` documents for other library
  ROMs) so real maze/background tiles get recorded as `<tile>` rules
  instead of the game replaying its own attract loop. That is a recording-
  input problem, not #339/#349, and per the task's boundary it was not
  chased further (no known entry script for this ROM exists in
  `scripts/stages/`, and finding/validating a new one was out of scope for
  this retest).

**All four completed runs failed criterion 3 for the identical reason:** a
full-screen captured `<background>` entry (priority ≥20 in every pack) is
drawn after, and wins over, every `<tile>` rule on the exact frame
`choose_frame` handed over. This is **not** #339/#349 — there is no gate
collision between two different captures in any of these four packs' logs;
Golf, Donkey Kong and Ice Climber each report a normal, uncontested
single-background match, and the Ice Climber evaluator's render even
surfaced the emulator's own log line naming the mechanism
(`[HD Pack] A <background> in this HD pack is drawn over <tile> rules, so
painting one of those tiles changes nothing on screen`). It is not a new
defect either: it is the same "background-capture override" precedence
class the original sweep already catalogued as known/off-limits in Mario
Bros., Tennis and Tetris 2 (ADR-0050/ADR-0156 — a captured background is
designed to own the cells its gate matches, drawn after the tile layer, and
nothing about the #339/#349 fix touches that design). It recurring in all
four of the newly-unblocked ROMs is not a coincidence worth chasing further
inside this task's boundary: these six ROMs were exactly the ones whose
whole recording *is* a captured background dominating the screen, so once
`choose_frame` can find *any* frame with tile rules drawn on it, the odds
that frame still sits inside that same background's gate are high. It is
the same known, out-of-scope limitation, now visible on four new ROMs
instead of blocking sandbox-prep outright.

Three of the four completed evaluators also opened a `hires.txt` (a
criterion-4 self-fail in two cases, and a self-flagged ambiguous case in
Ice Climber's, which read only the pipeline's own freshly-rebuilt copy and
said so explicitly) specifically to diagnose why their otherwise-correct
pipeline produced no visible change — the same "forced stop" pattern the
original sweep saw in 7 of 22 runs, always as an unforced post-build
verification check rather than a way to find the tile in the first place.

## Summary

- **PR #352 works, for what it targets.** Golf and Donkey Kong are clean,
  unambiguous confirmations: recordings that previously could not clear
  `choose_frame`'s whole-screen-capture-domination gate now do, with a
  normal, uncontested single-background match and real `<tile>` rules
  drawn on-screen. That is the specific failure this retest was asked to
  verify, and it is fixed.
- **3 of 6 ROMs are now fully unblocked past the #339/#349 gate**: Golf,
  Donkey Kong, Ice Climber. A 4th, Tetris, unblocks mechanically (no
  `PrepareError`) and produced a real, if partial, evaluator run. A 5th,
  Flintstones, unblocks mechanically but the frame it hands over has no
  confirmed on-screen shape, so its evaluator correctly declined. The 6th,
  Bubble Bobble, remains blocked outright — but for a different, genuinely
  distinct reason (see below), not a residual case of #339/#349.
- **None of the 4 completed evaluations reached a working end-to-end
  round-trip**, but not because of anything the #339/#349 fix was
  responsible for or could have prevented: all 4 hit the pre-existing,
  already-catalogued captured-background-precedence class (ADR-0050/
  ADR-0156), which the original sweep already filed as known/off-limits in
  Mario Bros., Tennis and Tetris 2. This retest did not discover a new
  product defect and, per the task's boundary, did not attempt to fix or
  re-file this known one.
- **Bubble Bobble is out of scope for a different reason.** Its recorded
  pack has exactly one captured background and zero collisions — there is
  nothing for ADR-0217/ADR-0218 to act on. The real blocker is that a
  short, no-input recording of this ROM never leaves its title/attract
  screen, so no real background art is ever captured as `<tile>` rules.
  That is a recording-input/duration limitation, unrelated to the fix
  under test.

## Honest limits

- **Criterion 1 is unscorable for this retest, exactly as the original
  sweep found**, and for the identical reason: every one of the 5
  evaluators dispatched here (4 completed + Flintstones' decline) reported
  the same `gitStatus` git-log leak, naming "Copy as MEP sheet cell" and
  `mep_add_cell.py`/ADR-0216 verbatim before they opened a single sandbox
  file. This retest's own worktree HEAD (`4d1a85c5`) still carries those
  commit subjects in its 5 most recent commits, so the leak was
  unavoidable here too. Checked for a fix to the dispatch/briefing
  mechanism itself before starting (per this task's instructions): none
  had landed on `main` as of this run — `git log -- scripts/
  f122_prepare_evaluator.py` still ends at the sonnet-sweep-doc commit
  (`d63ab5aa`) and the visible-window-marker feature (`c23f99b8`), neither
  of which touches dispatch. The parallel effort mentioned as in-flight had
  not yet merged.
- **The 4 completed evaluations are a small, correlated sample.** All 4
  came from ROMs whose entire pre-fix problem *was* a captured background
  dominating the screen; it is expected, not surprising, that the frame
  each one's fixed `choose_frame` finally settles on is still governed by
  that same background. This retest cannot say whether PR #352 introduces
  or worsens the captured-background-precedence class elsewhere — only that
  it did not prevent that pre-existing class from showing up here, on ROMs
  it could not previously even reach.
- **Two evaluators (Golf, Donkey Kong) opened `hires.txt` and self-scored
  criterion 4 a fail as a result**; a third (Ice Climber) opened only the
  pipeline's own freshly-rebuilt copy post-build and flagged the ambiguity
  of whether that should count, rather than picking the answer that favors
  it. None of the three used the read to find or copy a key by hand — all
  three used it only to diagnose an already-failed criterion 3 after the
  fact. This mirrors the original sweep's finding (7 of 22) almost exactly.
- No new product defect was found or filed. No commit besides this doc, no
  PR, and no GitHub issue came out of this retest — per the task, work on
  #339/#349/ADR-0217/ADR-0218 was not touched, only consumed.
