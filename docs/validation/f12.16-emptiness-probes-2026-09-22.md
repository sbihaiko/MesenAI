# F12.16 — emptiness probes as a last anchor pass (2026-09-22)

Scope and stop rule live in the PRD (Part A, row F12.16); the decision is
ADR-0223, accepted 2026-09-22, option A. Prerequisite: F12.15's split
overdraw tool (shipped, main), so the measure below is `erased background`
alone, on ADR-0221's Punch-Out!! route.

## What shipped

- `Core/NES/HdPacks/ScreenStitcher.h`/`.cpp` — `FlatRunColumns` (host-free:
  the grid columns a flat run spans, tile-boundary aligned to `fineX`);
  `AnchorChoice::UsedEmptinessProbe` (new counter); `SelectScreenAnchors`
  now explicitly excludes `Usage == UINT32_MAX` candidates from the
  stable/wide passes' pool (`order`), and, only when the stable/wide result
  still leaves rivals standing, runs one more greedy pass over the stable
  pool plus the flat cells no variant changes (`stableSubset`, factored out
  of the existing ADR-0159 §1 filter and reused for both pools) — kept only
  if it separates strictly more rivals than the previous best.
- `Core/NES/HdPacks/HdPackBuilder.h` — `AppendFlatAnchorCells` (new inline
  template method; host-bound, so it stays out of ScreenStitcher): for every
  flat run `CaptureScreen` would otherwise drop, expands it to every grid
  cell it covers and pushes an `AnchorCandidate` with `Usage = UINT32_MAX`
  plus a synthetic `ScreenRun` (same tile, `X` moved to the cell) into the
  same `pending.Cells`/`pending.Candidates` vectors the ranked, non-flat
  candidates use — so `choice.Picked` indices still resolve correctly when
  `FinalizeScreenAnchors` builds the `<background>`'s conditions.
- `Core/NES/HdPacks/HdPackBuilder.cpp` — `CaptureScreen` calls
  `AppendFlatAnchorCells` after building `ranked`/`pending.Candidates` as
  before; `FinalizeScreenAnchors` adds `emptinessProbeScreens` and the log
  clause "N screen(s) gated on an emptiness probe". Net **-3 lines** after
  the Codex-review fix below (2426 -> 2427 against the ADR-0137 ceiling of
  2428, not raised — the loop itself lives in the header).
- `scripts/core_unit_tests.cpp` — new tests, cited as ADR-0223 (BlocoP5):
  `TestAnchorEmptinessProbeSeparatesWhenOnlyFlatCellDoes`,
  `TestAnchorNonFlatCellSeparatesWithoutAProbe`,
  `TestAnchorFlatCellsNeverAppearInStableOrWideOutput`,
  `TestAnchorProbeOnACellAVariantChangesIsNeverChosen`,
  `TestSolidColourOneTileLandsInTheProbePool` — a synthetic `GridFrame` pair
  where only a flat cell separates capture from an addition-rival (probe
  chosen, rival separated); a pair where a non-flat cell already separates
  them (no probe used, last pass never needed to fire); one non-flat anchor
  plus flat probes only (a realistic candidate list per the Codex-review
  fix below: a screen with *no* non-flat candidate is never captured in the
  first place, so the stable/wide passes' own pool still resolves nothing
  by construction, and only the last pass, reported by `UsedEmptinessProbe`,
  separates the rival); a probe on a cell a third, genuine variant frame
  changes (excluded by the same stability filter as any other candidate,
  so no probe is ever chosen); and a solid colour-1 tile (plane0=FFx8,
  plane1=00x8) confirmed flat by the shared predicate and, once handed over
  with `Usage = UINT32_MAX`, resolved only via the probe pass.
- `Core/Core.vcxproj`/`.filters` — untouched (no new files; `ScreenStitcher`
  and `HdPackBuilder` already registered).

## Codex review, same day (PR #379)

Two findings on the original commit, fixed in the same worktree, uncommitted
(coordinator commits separately):

- **Finding 1 (accepted, code change):** `CaptureScreen`'s local `isFlat`
  lambda tested "all 16 bytes identical", not ADR-0221/ADR-0223's definition
  of "empty" (`MesenSheets::IsFlatTileData`, the same per-plane predicate
  `FlatShapePlane` uses). Fixed: the lambda is gone, both `ranked`'s
  exclusion and `AppendFlatAnchorCells` (now a plain method, no longer a
  template — the `IsFlatFn` parameter is unnecessary once there is one
  predicate) call `MesenSheets::IsFlatTileData(run.Tile.TileData)` directly.
  This moves ADR-0050's candidate set at the margin, as flagged in the
  finding: a 0x55-striped tile (16 identical bytes, not flat) is now a
  candidate in `ranked` instead of being (wrongly) treated as flat; a solid
  colour-1/2 tile (all-0xFF or all-0x00 per plane, but not "all 16 bytes
  identical" — e.g. FFx8+00x8) now goes to the probe pool instead of the
  rarity ranking. New unit case `TestSolidColourOneTileLandsInTheProbePool`
  covers exactly this margin tile.
- **Finding 2 (decision, no behaviour change):** kept the early `return`
  in `CaptureScreen` when the non-flat pool (`pending.Candidates`, built
  from `ranked` before `AppendFlatAnchorCells` runs) is empty. A gate made
  only of emptiness probes would fire on every blank screen, worse than not
  drawing; ADR-0050 requires at least one non-flat anchor and this slice
  does not relax that. Rationale is now in the comment at the `return`
  itself. `TestAnchorFlatCellsNeverAppearInStableOrWideOutput` was rewritten
  to stop implying a flat-only capture exists — its candidate list is now
  one non-flat anchor (that does not by itself discriminate) plus the flat
  probe, matching what `SelectScreenAnchors` is actually ever handed.

**What moved after the predicate fix**, same route, same ROMs:

- Punch-Out!! (the ADR-0221 route): **nothing moved**. Same summary line (10
  anchored, 228 addition-rivals, 6 gated on a probe), same 10 -> 9 captures,
  same 0.1200 -> 0.0865 draw rate, same 0/0 on the full 36-point sweep. The
  card's probe tile (`FD`) happens to be a genuine "all 16 bytes identical"
  flat tile (confirmed uniform under both predicates), so this ROM's own
  numbers don't move — the margin the fix touches (0x55-stripe, solid
  colour-1/2-but-not-uniform-byte) isn't present at these specific cells.
- 30-ROM library: captures unchanged (193 -> 219 either way); probes rose
  **58 -> 59** (F-1 Race gained one, 0 -> 1); condition-changed packs rose
  **13 -> 14** (F-1 Race); Ninja Gaiden's mean draw rate shifted
  0.0771 -> 0.0656 and Pac-Man's 0.0916 -> 0.0902 (same capture counts on
  both), consistent with a probe or ranking cell moving between the two
  pools on those ROMs without changing which screens get captured.

## Not verified

- No pre-F12.16 dylib was built fresh in this worktree to reproduce the
  "before" side of either measurement directly. The sweep's "before" figure
  (437, F12.13's old-dylib-no-tag log) and the library's "before" side
  (F12.13's already-recorded `lib-after/` packs) are both taken from a prior
  session's binaries/artifacts, not rebuilt and re-measured against source
  in this pass — only the "after" (F12.16) side was built and measured here.
  Both are traceable (sha256s above for the after-side binaries; the
  before-side packs still exist on disk and were confirmed present), but
  they were not independently reproduced.
- The full-sweep 0/0 total cannot be attributed solely to this slice: the
  pack recorded also carries F12.15's `<bgPreservesBehindBgSprites>` tag, so
  the run measures the two mechanisms stacked, not F12.16 in isolation
  against a tag-off baseline.
- The library table's "packs whose `<condition>` lines changed" (14 of 30)
  is a line-level diff of `hires.txt`, not a semantic diff — it does not
  distinguish a probe's `<tileAtPosition>` line being added from some other,
  unrelated builder change touching the same pack between the two sessions'
  binaries (F12.13's dylib and this slice's).

## Deviations from the ADR/PRD

None known. `AppendFlatAnchorCells` living in the header (rather than
`ScreenStitcher.cpp`, which is host-free) is a placement choice forced by
`ScreenRun` being an `HdPackBuilder`-private type and the ADR-0137 ceiling
leaving zero headroom in `HdPackBuilder.cpp`; the arithmetic it depends on
(`FlatRunColumns`) is in `ScreenStitcher.cpp` as intended. `AppendFlatAnchorCells`
dropped its template parameter in the Codex-review fix (one predicate now,
`MesenSheets::IsFlatTileData`, so `IsFlatFn` was unnecessary) — not a
deviation, a simplification the same fix already required.

Reproduced from the artefacts, not re-quoted, **before** the Codex-review
fix: 990/990, `HdPackBuilder.cpp` at 2428, 9 `<background>` lines, the four
`FD` probes at rows 120/136/176/200, the recorder line ("6 screen(s) gated

(4 -> 23) / Pac-Man (17 -> 25) counts — the new captures pixel-diff as
distinct backgrounds (platform / dot-state changes), not one screen
fragmented. Verdict PASS, all three stop conditions met. Superseded by the
Codex-review pass above for exact counter values (`HdPackBuilder.cpp` now
2427, tests now 992) — every reproduced number here still holds on
Punch-Out!! after the fix; only `HdPackBuilder.cpp`'s line count and the
unit-test total moved.

On the isolation caveat above: the F12.15 tag only gates
`DrawBehindBgSprites`, so it can move the `erased sprite` column and never
the `erased background` one. The 374 -> 0 on `erased background` is therefore
F12.16's alone, column-wise, without a second binary; the caveat stands only
for the sweep *total*.
