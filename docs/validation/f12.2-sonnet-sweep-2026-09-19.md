# F12.2 — the artist-surface cold read, 28 ROMs, Sonnet as the evaluator

**Date:** 2026-09-19
**Evaluator:** 22 fresh Sonnet sessions (`general-purpose`, `model: "sonnet"`
explicit on every dispatch), one per game — 6 of the 28-ROM library never
reached dispatch (see *Not evaluable*)
**Dispatcher:** this session, with `scripts/f122_prepare_evaluator.py`
(patched — see *The dispatcher's own defects*), run against a fresh
worktree checkout with its own copy of `runs/f12.2-sweep/{roms,packs}`
**Briefing:** `docs/validation/f12.2-sweep-evaluator-briefing.md`, reused
near-verbatim, with one line added asking each evaluator to log the
git-status leak described below if it saw one

ADR-0214 is the standing decision that a fresh Opus session is the
evaluator for an artist-surface cold read. This run does **not** change
that decision. It is a one-off comparison: the same 28-ROM library, the
same protocol, the same briefing, with Sonnet in the evaluator seat instead
of Opus, to see whether the panel's findings hold across models. The
95%-confidence framing from the Opus sweep applies here too: 22 games is
still a sample, not a census, but it is enough to tell "this game's pack is
odd" apart from "the feature is broken."

## What is different from the Opus sweep, and why it matters more here

Every dispatched evaluator in this sweep ran as a Sonnet `general-purpose`
agent spawned by the `Agent` tool from inside this git worktree, under this
user's account. Two properties of that dispatch mechanism turned out to
leak the answer to criterion 1 (findability) into the evaluator's context
before it ever opened the sandbox:

1. **Git-status leak.** The harness auto-injects a `gitStatus` system
   reminder into every session/subagent operating inside a git repository,
   including the branch's recent commit log. This worktree's recent commits
   include `feat(ui): Copy as MEP sheet cell puts a cell on the clipboard,
   unplaced` and `feat(scripts): mep_add_cell.py places a copied cell
   (ADR-0216)` — naming, verbatim, the exact menu action criterion 1 asks
   the evaluator to find unprompted. **18 of the 22 dispatched evaluators
   explicitly noticed and logged this** (1942, Castlevania, Excitebike, and
   Contra did not report it, most likely because their briefings predated
   the line added asking evaluators to check for it, not because they were
   spared it). It should be treated as present in all 22 runs.
2. **Global-memory leak (worse).** One evaluator (The Legend of Zelda)
   reported that its own standing user-level memory file — loaded at
   session start independent of git status, for every Claude Code session
   under this account — already documented this exact feature, its menu
   label, and a prior "F12.2" closure. This is a categorically deeper
   contamination than the git log: it does not depend on which repo the
   session runs in, only on which account it runs under. It almost
   certainly affected all 22 dispatches equally.

**Consequence:** criterion 1 cannot be scored as a genuine cold find for
any ROM in this sweep. This is a defect in how *this specific sweep*
dispatched evaluators — general-purpose agents under this account, in this
worktree — not in the emulator, the MEP tooling, or ADR-0214's protocol
itself (a truly isolated evaluator session, e.g. one without this
worktree's history and without this account's memory files, would not have
this problem). It is unknown whether the original Opus sweep's dispatches
had the same exposure; if they used the same `Agent`-tool mechanism from
inside this repo, they likely did, whether or not that sweep's account
called it out. This is the headline methodology finding of this run and
should inform how any future sweep is dispatched (a worktree with no
history beyond the sandboxed content, or a session outside this harness's
default memory-loading, would close both leaks).

Every other criterion (2, 3, 4, 5, 6) was unaffected by this and is scored
normally below.

## The 28-ROM library, and why only 22 were dispatched

Six of the 28 ROMs never reached evaluator dispatch: **Bubble Bobble,
Donkey Kong, Golf, Ice Climber, Tetris, The Flintstones**. Each failed the
sandbox-prep step (`f122_prepare_evaluator.py choose_frame`) identically,
at every candidate second (10/20/30/40/50/60s): the screen is drawn by a
captured whole-screen `<background>` rather than by any single background
`<tile>` rule, so the tool has no frame to hand an evaluator where the
picked shape's provenance is a `<tile>` rule and not a screen capture. This
is the same failure class as issues #339/#349 (whole-screen capture
precedence), tied to the in-flight `ADR-0217`/`ADR-0218` branch — explicitly
out of scope for this task to touch, re-file, or fix. Per the task's own
boundary, these 6 are recorded here as not-evaluable and were not
investigated further.

**This sweep's not-evaluable rate is markedly higher than the Opus
sweep's:** 6 excluded before dispatch here, against the Opus sweep's 2
(Double Dragon, Mega Man, both sprite-only-frame exclusions). On top of
that, 3 more of the 22 *dispatched* ROMs turned out to be not-evaluable
once the evaluator actually looked at their inputs:

- **Gauntlet** — the tilemap/copy-table dump covers only one of the two
  nametables a split-screen title uses, with no viewport box to say which
  half is visible; 0 of 25 distinct tile keys could be honestly called
  on-screen shapes. The evaluator declined to guess and stopped before
  pasting anything.
- **Ninja Gaiden** — the tilemap PNG and copy table are truncated to tile
  column 0 only (30 lines, all `col=0`), despite the index's own claim of
  828/960 blocks explained. The rock the evaluator wanted to recolor sits
  two-thirds across the screen, nowhere near column 0.
- **Pac-Man** — the paused frame is the attract-mode character/nickname
  screen, entirely sprite-drawn; the copy table's 96 entries are all the
  blank tile. Same exclusion class as Double Dragon/Mega Man in the Opus
  sweep, and the index file had already flagged it.

Counting all nine, this sweep's effective not-evaluable rate is 9/28
(~32%), against the Opus sweep's 2/30 (~7%). Gauntlet and Pac-Man's causes
are known, already-documented dispatcher-tooling gaps (see below); Ninja
Gaiden's column-0 truncation is new and unexplained — see *The dispatcher's
own defects*.

## What the runs found

### Confirmed recurrences of already-known issues (not re-filed, per task boundary)

- **Nametable/window ambiguity** (already catalogued as a dispatcher defect
  in the Opus sweep): recurred in Dr. Mario, Super Mario Bros. (resolved
  correctly by the evaluator), Zelda II, and — in its most severe form,
  blocking dispatch entirely — Gauntlet. The copy-table dump does not
  reliably say which of a game's nametables, or which window into a
  scrolling one, corresponds to the paused frame the evaluator was shown.
- **Whole-screen captured-`<background>` overrides the sheet-cell tile**
  (ADR-0050; the same precedence class as issues #339/#349, tied to the
  in-flight `ADR-0217`/`ADR-0218` branch): recurred in Mario Bros., Tennis,
  and Tetris 2 — all three static title/menu screens, which is exactly the
  kind of frame a bootstrap capture freezes wholesale. Per the task's
  explicit boundary this is noted, not re-filed or fixed.

### New findings from this sweep

1. **The index's self-reported tile coverage does not match the actual
   copy-table dump, for at least two games.** Contra's index claimed
   "692/930" tile blocks explained; the actual `tilemap-copy/*.txt` had 90
   lines. Mike Tyson's Punch-Out!!'s index claimed 793/960; the actual
   dump had 32. Both evaluators had to independently re-measure the dump
   before they could trust it enough to pick a tile. This is sweep-tooling
   (`f122_prepare_evaluator.py`'s coverage-count computation vs. its actual
   dump write), not the shipped Tilemap Viewer or "Copy as MEP sheet cell"
   feature, so it is recorded here rather than filed as a product bug.
2. **Ninja Gaiden's tilemap/copy-table dump is truncated to tile column 0
   only**, independent of and more severe than the general nametable/window
   ambiguity above (that ambiguity is about *which* nametable/window; this
   is a dump that never covers more than 1 of 32 columns at all). Also
   sweep tooling, not filed as a product bug, and not root-caused within
   this task's scope.
3. **A correctly-authored, correctly-built, correctly-linted sheet cell can
   silently fail to render, with nothing in the build or lint output able
   to catch it**, independent of both known issues above. Metroid's
   evaluator went furthest in isolating this: after a clean build/lint with
   a new cell, it directly overwrote the pack's own **pre-existing,
   already-shipping** art for the identical tile+palette key (no new key,
   no precedence question) and still saw zero change on the rendered
   frame — while the pack's font/logo repaints elsewhere on the same frame
   visibly worked. This, and the same signature in Dr. Mario and Zelda II
   (clean build, key confirmed present at the correct coordinates, zero
   render change), is consistent with the nametable/window ambiguity's
   likely mechanism (the copied tile's palette/attribute pairing may not
   match what the PPU actually drives for that pattern on that exact
   frame) rather than a new, independent one — but Metroid's
   overwrite-the-existing-art test is stronger evidence than either the
   Opus sweep or the rest of this one produced, and is worth a follow-up
   investigation with live PPU/attribute inspection, which was out of
   scope for a sandboxed evaluator and out of scope for this task's time
   budget.
4. **Dispatcher game-identity mismatches.** Metroid's index file is named
   `Metroid__USA_.md`; every dispatch in this sweep (mine, following the
   ROM-library naming from the earlier sandbox-prep run) referred to it as
   `Metroid__1986___Nintendo_`, which does not exist anywhere in the
   sandbox. The evaluator correctly found the one plausible match and
   proceeded, logging the mismatch. Separately, Lemmings' sandbox files are
   all dated 1993, not 1991 as this sweep's dispatch prompt said. Both are
   naming inconsistencies in how this sweep's own game list was compiled
   (most likely copied from a stale ROM-library listing), not a defect in
   `f122_prepare_evaluator.py` itself, and not worth filing.
5. **Evaluator confusion, not a defect:** two evaluators (The Legend of
   Zelda, Tennis) tried `tools/mep_addition.py --help`/no-args, got silent
   exit 0, and treated it as a CLI usability gap. Checked directly:
   `scripts/mep_addition.py` is a pure library module (ADR-0196's addition-
   tag logic), imported by `mep_build.py`/`mep_lint.py`/`compose_engine.py`,
   with no `__main__` block at all — there is nothing to discover because
   it was never meant to run standalone. Not filed.

## Honest limits

- Criterion 1 is unscoreable for this entire sweep, for the dispatch-
  mechanism reasons above — this is the sweep's own limit, not a limit of
  the feature under evaluation.
- 9 of 28 ROMs (32%) produced no evaluation at all, more than four times
  the Opus sweep's rate, entirely concentrated in the two already-known
  dispatcher-tooling gaps (whole-screen capture domination, nametable/
  window ambiguity) plus one new, unexplained truncation (Ninja Gaiden).
- The silent-no-render pattern (finding 3 above) recurred in exactly the
  three ROMs that also would have been the cleanest confirmations of
  criterion 5 (Dr. Mario, Metroid, Zelda II) — meaning this sweep cannot
  positively confirm the round-trip's *rendering* half held up for those
  three games, only that the *authoring* half (JSON in, `<tile>` rule out)
  did.
- No new genuine, reproducible product defect from this sweep met the bar
  for filing a bug: every finding not already covered by an existing,
  off-limits issue (#339/#349) or an already-catalogued dispatcher defect
  (nametable/window ambiguity) turned out to be either sweep-tooling
  (coverage-count mismatch, Ninja Gaiden's truncation) or evaluator
  confusion (`mep_addition.py`). No commit, no PR, and no new GitHub issue
  came out of this run.
