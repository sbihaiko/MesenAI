## Result

**Criterion 3: 20 of 28** on the same 28 ROMs (2026-09-19: 13 of 28). The
scorer and the evaluators agree on every row.

- **11 passes needed nothing but the path.** 1942, Bomberman, Castlevania,
  Contra, Excitebike, F-1 Race, Lemmings, Lifeforce, Mega Man 2,
  Mike Tyson's Punch-Out!! and Super Mario Bros. 3.
- **9 passes also retired a captured screen** through the guide's
  *Retiring a capture* (#344): Bubble Bobble, Donkey Kong, Golf, Ice Climber,
  Mario Bros., Metroid, Pac-Man, Tennis and Tetris. That section is the
  supported path on this `main`, so these count as passes. In 2026-09-19
  terms, "no folders moved aside", the figure is 11 of 28.
- **4 of the 20 passes painted a blank tile** (Bubble Bobble, Contra,
  Punch-Out!! and Pac-Man): the copy table the dispatcher handed over offered
  no other key. Those runs prove the plumbing, not that an artist can pick a
  shape. Excluding them, 16 of 28 painted a real shape.
- **8 fail.** Seven of them (Dr. Mario, Gauntlet, Ninja Gaiden, Super Mario
  Bros., Tetris 2, The Flintstones and The Legend of Zelda) share **one**
  cause, A below: the copy resolves keys through a scanline trace left over
  from before the save state was loaded. The eighth, Zelda II, fails on two
  dispatcher-harness defects, B and C. Every failure has a named cause and a
  bug on the board (*Bug entries*: #419–#421). None is a non-goal.

**Criterion 4: 27 of 27 dispatched runs.** Nobody opened `hires.txt`. On
2026-09-19 the Tennis run had grepped it because nothing confirmed the copy.
This time every run checked its key through `mep_add_cell.py`'s output or a
`build` line instead.

**Criterion 2: 27 of 27.** Every run pasted the copy line as-is and let
`mep_add_cell.py` place it. No run hand-edited `index`, `x`, `y`, `count`, or
the sheet.

**Criterion 1: void on all 27 runs, not scored.** Every evaluator named
`Copy as MEP sheet cell` from the label dump within 2 to 55 s. Every
evaluator also logged contamination that reached it before the dump:

- the harness's auto-loaded memory index names F12.2 as shipped with a
  placer;
- the gitStatus reminder carries F14.x commit subjects;
- the briefing itself names `f12.2-copy-sheet-cell-panel-script.md`.

See deviation 6. The 2026-09-19 figure (28/28) stands as the last clean
measure of the label.

**Criterion 7: 27 of 27 under 20 minutes.** Runs took 1 min 00 s to
2 min 27 s from start to magenta or give-up. On 2026-09-19 they took
1 m 28 s to 7 m 33 s.

## Causes of the remaining failures

These were measured in-process by a separate Opus investigation with a
temporary, since-deleted diagnostic test. It ran the scan's exact flow twice
per game: once as the scan does it (`a0`), and once with about 100 ms of
emulation after the state load (`a100`).

**A. The copy resolves the key through the scanline trace left over from
before the state load.**

- `CopyAsMepSheetCellTests.cs:159-167` loads the `.mss` and emulates nothing
  afterwards.
- A save state does not carry the per-scanline trace ADR-0215 resolves
  through (`Core/NES/BaseNesPpu.h:145,164`). ADR-0215's own "Correction,
  2026-09-19" says so.
- So `NesDrawnTileResolver` (`UI/Logic/NesDrawnTileResolver.cs:95-122`, via
  `HdPackCopyHelper.cs:143,194-206`) resolves every tile through a boot frame
  about 30 frames after power-on. Every `a0` run logged
  `trace identical to pre-load: True`.
- Before ADR-0215, the copy read the paused CHR mapping, which a state load
  does restore. That is why Super Mario Bros. and The Legend of Zelda passed
  on 2026-09-19 and copy nothing now.
- The warm-up before the load is wall-clock (500 ms), so the stale frame
  varies between runs. The diagnostic's `a0` got 12 copies on SMB, where the
  real scan got 0.

| Game | As scanned (stale trace) | One frame emulated after the load | Pack's rule |
|---|---|---|---|
| Super Mario Bros. | 948 of 960 refused "no visible scanline drew" (rendering off on the boot frame) | 778 copied, 182 correctly off-screen | -- |
| The Legend of Zelda | 451 refused "not drawn" | 569 copied | -- |
| Dr. Mario | tile 0,0 → 1276 (`$01FC0` resolved as page `$4000`) | 252 | 252 |
| Ninja Gaiden | 7162 / 7160 (bank `$1B000`) | 7930 / 7928 (`0x1EFA` / `0x1EF8`) | 7930, `020F3036` |
| Gauntlet | 2304–2317 (page `$10` → `$9000`) | 1024 | 2304 is a sprite rule |
| Tetris 2 | 112 | 4464 (`0x1170`) | `0x1170` / `0x1171` |
| The Flintstones | 16 | 14352 (`0x3810`), the runtime's `0x38C7` bank | `0x3810` |

- One cause covers all five wrong-bank rows and both empty tables.
- #341's fix is correct when it is handed a fresh trace, and #341 stays
  closed.
- Gauntlet's "every cell dimmed" follows from A too. The stale keys are not
  on the frame, so the dispatcher's tilemap dims every cell.
- **This is not only a harness defect.** A person who loads a save state
  while paused and then copies from the tilemap viewer gets the same stale
  trace. Loading a state and copying before unpausing is an ordinary artist
  move.
- Not verified: the small within-bank gap between the fresh-trace index and
  the runtime's (Tetris 2's 4464 vs the evaluator's 1171; Flintstones'
  `0x3810` vs `0x38C7`). These are probably different cells or frames.

**B. The scan checks palettes against the bootstrap `auto/` pack, not the
pack the evaluator paints.**

- The scan's home has an empty `HdPacks/`, so the pack the core loads is the
  bootstrap `<rom dir>/<stem>/auto`, whose `defaultTile=Y` rules act as
  palette wildcards (`UI/Logic/NesPackTilePalette.cs:78`).
- Every copy table predates the `mep/` it is compared against (Zelda II:
  00:23:32 vs 00:25:31).
- Zelda II's tile 376 therefore copies with the live palette `0F301C15`. The
  baseline pack keys it only as `0F2B0F00`.
- B also let A's stale keys through: Tetris 2's 112 and Flintstones' 16 have
  no rule in the baseline pack and would have been refused against it.
- `scripts/f122_prepare_evaluator.py:582-597` never installs the baseline
  pack before the scan. This is a dispatcher defect.

**C. The scan walks nametable `$2000` only.**

- `CopyAsMepSheetCellTests.cs:345-346` walks x < 256, y < 240.
- Zelda II's title shows nametable 0 rows 12–29, then nametable 2 from
  about scanline 144. Its copy table holds a row-0 rock band and blank tiles,
  and "0 of its 10 keys are non-blank shapes".
- Gauntlet shows nametable 2 rows 0–11, which are never walked. SMB scrolls
  into nametable 1.
- The same one-nametable walk is why several passing tables (Bubble Bobble
  96 cells, Contra 90, Pac-Man 96, Punch-Out!! 32, Ninja Gaiden 30) offered
  only a blank tile. That makes 4 passes "blank tile" and not "shape".
- 2026-09-19's dispatcher defect 8 named this. It is still open.

**D (minor, no failure of its own).** `GetNesHdPackTilePalettes`
(`InteropDLL/DebugApiWrapper.cpp:333-370`) returns background and sprite rules
together, so Zelda's blank tile comes back with 31 palettes, several of them
sprite palettes. That inflates #342's "ambiguous" refusals: 391 on Zelda even
with a fresh trace. It is a #342 follow-up, not a bug of its own.

## Bug entries

Filed with `scripts/report-bug.sh` on 2026-09-24: entry 1 is #419, 2 is
#420, 3 is #421, and the passing-runs finding below is #422.

1. **(P1, #419) Copy as MEP sheet cell resolves keys through the pre-load
   scanline trace after a state load.**
   - Repro: `MESEN_F122_COPY_SCAN=<Dr. Mario .nes>
     MESEN_F122_COPY_STATE=<the F14.2 Dr. Mario .mss>
     MESEN_F122_COPY_OUT=/tmp/x.txt make headless-ui-tests`. Equivalently,
     in the GUI: pause, load a state, and copy from the tilemap viewer
     without unpausing.
   - Expected: tile 0,0 copies as index 252, and every drawn cell of the
     shown frame copies.
   - Observed: 1276 on Dr. Mario, wrong-bank indices on Ninja Gaiden,
     Gauntlet, Tetris 2 and The Flintstones, and an empty table on Super
     Mario Bros. and The Legend of Zelda. All are silent and well-formed, and
     `build` and `lint` are green on the pasted key.
   - Fix direction, not applied: invalidate the trace on state load and
     refuse until a frame has been drawn, or step one frame after the load.
     The scan should step one frame in any case.
2. **(P2, #420) The F12.2/F14.2 copy scan checks palettes against the bootstrap
   `auto/` pack, not the pack the evaluator paints.**
   - Repro: prepare Zelda II with `scripts/f122_prepare_evaluator.py`, then
     read tile 28,0 in the copy table.
   - Expected: palette `0F2B0F00`, the only palette the baseline pack keys
     for that tile.
   - Observed: `0F301C15`, accepted through the `auto/` pack's
     `defaultTile=Y` wildcard. It also lets stale keys through (Tetris 2,
     The Flintstones).
3. **(P2, #421) The copy scan walks only nametable `$2000`.**
   - Repro: prepare Zelda II or Gauntlet, then compare the copy table with
     the frame.
   - Expected: a copy line for every visible background cell, from whichever
     nametable drew it.
   - Observed: no lines for the visible cells drawn from nametable 1 or 2.
     Zelda II's table has no non-blank shape on screen, and four passing
     games offered only a blank tile.

## What the passing runs still found

These are ranked by how many of the 27 runs named them. None blocked a pass.
They are defects and observations, not criterion-3 failures. Where one looks
like a real bug, it is marked; the rest are for triage.

1. **`build` stays silent when a captured screen hides a freshly painted
   key. 10 runs** (Bubble Bobble, Donkey Kong, Golf, Ice Climber,
   Mario Bros., Mega Man, Metroid, Pac-Man, Tennis, Tetris).
   - The guide says a painted tile a capture also draws gets its own `(#338)`
     line, and that no line means the paint reached the pack. On every one
     of these runs the only per-capture signal was the emulator's render log.
   - On Ice Climber and Pac-Man, `build` named a *different* capture than the
     one covering the frame (`screen002`/`screen013` vs
     `screen004`/`screen012`).
   - Retiring one capture exposed the next on Ice Climber, whose run had to
     retire all 25.
   - Filed as #422: **(P2) `mep_build`'s #338 warning does not fire for a
     cell added by `mep_add_cell.py`, or names the wrong capture.**
     - Repro: Mario Bros. F14.2 frame; add the tile at 0,9 with
       `mep_add_cell.py`, paint it, then build.
     - Expected: a `(#338)` line naming `screen002`.
     - Observed: only the generic "N captured screens override tiles" line.
2. **Retiring a capture regresses the rest of that frame's art** (Tetris
   "PUSH" → "PNSH", Tennis crowd and sign, Metroid ground, Mega Man's title).
   The guide offers no way to let one tile show through a capture short of
   editing `hires.txt`, and the runtime log still suggests changing the
   `<background>` priority. This is the ADR-0050/ADR-0156 trade-off, logged
   as an observation, not a bug.
3. **The dispatcher's tilemap dims cells that are on screen** (1942, Excitebike,
   Dr. Mario, Mega Man, Metroid, Mega Man 2, SMB3, Tetris, Tetris 2,
   The Flintstones). This is a dispatcher defect: the "on this screen"
   shading comes from the stale trace (A) and the one-nametable walk (C).
4. **The copy prints the index in decimal and `build` prints it in hex**
   (Lemmings, Mario Bros., SMB3). An artist has to convert by hand to find
   their line in `build`'s output.
5. **`build`'s output is too noisy to read.**
   - `overrides` / `loses` info lines run from about 75 KB to 1 780 lines.
   - Lint's standing "not a multiple of 32" warnings, 29 to 38 per pack, bury
     the lines that matter (Mega Man 2, Mario Bros., SMB3, Tetris 2).
   - When a key has two cells on one sheet, `build` does not say which won
     (Lifeforce).
6. **`mep_add_cell.py` warnings.**
   - It reports a key "already claimed" by cells whose `index` differs
     (Punch-Out!!: 509 vs 765–767).
   - It truncates keys in the claim list (Tennis).
   - It does not print the key it placed (Mega Man 2).
   - `--dry-run` fails after the pack argument (Gauntlet).
   - It accepts an index far outside the pack's range without comment
     (The Flintstones: 16 vs ~14 500).
7. **Retire bookkeeping.**
   - Its warning names `auto/textures/` on a work copy that has no `auto/`
     (Golf, Mario Bros., Mega Man).
   - It leaves `screenNNN.orig.png` orphaned (Tennis).
   - Ice Climber moved 24 PNGs and was told "retired 22".
   - The core log says "N captured screens — not used under the human
     layer" in the same run in which one is drawn over the tiles (Mario
     Bros., Tennis).
8. **The render ends one frame after the saved state** (F-1 Race, Lifeforce,
   Mega Man 2). The sprites and, on Mega Man 2, a 4 px scroll differ from the
   reference frame. The background criterion is unaffected.
9. **The copy receipt (#340) is not what the briefing describes.** The
   briefing still says "no toast". Several runs logged "no feedback after the
   copy", but those runs worked from the dispatcher's copy table, not the
   GUI. This is briefing staleness, deviation 4.

## Protocol and deviations

Same as 2026-09-19 unless listed:

- the same 30 ROMs;
- each recorded for 60 s with `headless_record ... bootstrap log` into its
  own folder;
- `auto/` copied to the baseline pack and built with `mep_build.py build`;
- `f122_prepare_evaluator.py` picks the frame, mints the `.mss`, draws the
  tilemap, runs the copy scan and makes the work copy;
- one fresh Opus evaluator per game on the sandbox briefing, with a 20-minute
  budget;
- `f122_score_panel.py` on the pack the evaluator left behind, against the
  unpainted baseline.

Deviations:

1. **Frame fallback on seven games.**
   - `f122_prepare_evaluator.py`'s `choose_frame` refuses a game whose
     captures own every sampled second. That happened on Donkey Kong, Golf,
     Ice Climber, Mega Man, Tetris, The Flintstones and Double Dragon.
   - A dispatcher-only wrapper
     (`scratchpad/f142/prepare_fallback.py`, not versioned) handed over the
     40 s frame (20 s for Tetris and The Flintstones), as the 2026-09-19
     prepare did before the refusal existed.
   - This lets the evaluator exercise #344's retire path on those games.
   - Of those seven, all but Double Dragon (no table) were dispatched, and
     all but The Flintstones passed.
2. **Absolute paths.** The first prepare run passed `--sweep` as a relative
   path. The scan's `dotnet test` then resolved the ROM from another cwd and
   skipped silently ("the scan wrote no table" on every game). The run was
   redone with absolute paths, and that is the only run this log reports.
3. **`tools/` carries 11 modules** (the AST import closure, including
   `mep_add_cell.py`), and the dispatch prompt adds one line mapping the
   guides' `scripts/<tool>.py` to `tools/<tool>.py`. On 2026-09-19 there was
   no placer to map.
4. **The briefing is stale against this `main` and was not edited**, so that
   F14.2 uses the same briefing as 2026-09-19.
   - It says "no toast", but #340 added one.
   - It lists three tools, while the guide's short path uses
     `mep_add_cell.py`.
   - It says `mesen-home` lands beside the prefix; it lands inside.
   - Its first paragraph names `f12.2-copy-sheet-cell-panel-script.md`.
   - Several runs logged these; none cost a pass.
5. **The ROMs live inside the repo worktree** (`runs/f14.2-sweep/roms/`),
   not in the sandbox. The agent harness's worktree guard refused some
   evaluators' compound render commands for that reason. They split the
   commands, at a cost of about a minute each.
6. **No blind worktree and no memory redaction**, the same as the 2026-09-19
   Opus sweep. That is why criterion 1 is void on every row, not scored.
7. **The dispatch prompt forbids git writes and `gh`** (an F14.2 hard rule).
   No run needed either.
8. **`out/` is shared.** An evaluator could read another game's `out/`
   folder. No log reports doing so.

## Honest limits

- One evaluator model, one dispatch each. A run is scored by what it reached.
- The copy tables are the dispatcher's scan, not a person's clicks. Cause A
  means seven of the eight failures measure the scan's state-load path.
  Clicking in the GUI after playing to the frame, instead of loading a
  state, would likely have copied the right key on those games. That is not
  measured here, so they are counted as failures, with the cause named.
- Retirement passes (9) buy the magenta by giving up the capture's other art
  on that frame, as item 2 above records.
- Every number above comes from `out/log-<game>.md` in
  `~/f14.2-opus-sandbox/` or from `runs/f14.2-sweep/score/<game>.txt`. Neither
  is versioned, like the recordings, `.mss` files and ROMs.
