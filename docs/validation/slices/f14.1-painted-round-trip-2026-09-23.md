# F14.1 — the painted round trip in the running game (2026-09-23)

Scope and stop rule live in the PRD (Part A §4, Phase 14, row F14.1). The
decisions under test are ADR-0220 §5 (the flat PNG over the F12.4 name is the
return path; F12.11 stop condition (3)), ADR-0209 Q2 = (e) / Q3 = (i) (a
figure exported whole and imported back onto its cells) and ADR-0212 (the
in-place reload). Go-ahead, verbatim: *"Sim, como recomendado (Recommended)"*
(2026-09-23).

One painted cell reaches the running game pixel-exact through the F12.3 reload
twice — once from a stroke on the `paint` layer of a kit `.ora` exported flat,
once from a stroke on a `mep_figure.py export` figure brought back with
`mep_figure.py import` — each against an unpainted control of the same run
that differs at exactly the painted pixels. It also found one defect in the
documented figure loop (§5), which this log does not fix.

## 3. The installed pack and the replay

Every in-game run installs a built project's `textures/*` as the loose pack
`<run>/mesen-home/HdPacks/Contra/` of its own home. The output prefix is
`<run>/out` — a file name, not a bare directory — so each run has its own home,
and the pack's own log line proves it loaded. It then replays the recording's
own input from the minted state for the recording's own length, with
`mep-off`, and captures the final frame:

```sh
scripts/headless_record <run>/rom/Contra.nes 61 <run>/out capture screenshot mep-off \
  input=scripts/stages/contra/stage1-probe.txt state=<f141>/stage1.mss \
  [reload-at-frame=3000 replace=<run>/mesen-home/HdPacks/Contra/sheets/<sheet>.png=<painted>/<sheet>.png]
```

Every run logs `[MEP] textures: loaded loose NES HD pack from
HdPacks/Contra/hires.txt (493 tiles, scale 4)` and captures `1024x960
frame=5470` — the 4x HD render, on the same emulated frame.

**Compared frame: 5470**, the run's last. The input script runs dry at frame
5392 (1804 + 3588), and the player stands still for the last 78 frames. The
reload fires at **frame 3000**, mid-play, 2470 frames before the compared frame.
The reload trigger counts emulated frames, not seconds.

### Choosing the cell, before painting anything

§3.2 of the F12.11 follow-up log picked a `spriteNearby`-gated cell and never
saw it on the one frame it compared. This time the cell was chosen from the
compared frame itself. One exploratory run gave every cell of `usr003` (the
kit's rest grid, `pose001`, `pose003`, …) its own flat colour, and the frame-5470
screenshot was searched for each colour. Cells 0–10, the eleven drawn tiles of
`pose001`, the standing player, are on screen. **Cell 3** (1x `(1, 10)`,
sheet pixels `(4, 40)`–`(35, 71)`, key
`5E5E5D733D1F0F0F6161634E23100C0F` / `FF36160F`, the torso) is the only one
drawn with all 1024 of its pixels, unoccluded, at frame `(484, 364)`–`(515, 395)`.
Its three rules in the built pack (`[spr011_n2]`, `[spr013_n2]` and the plain
fallback) all point at the **same crop**. Whichever rule wins, the same pixels
are drawn, so no condition can hide a repaint of this cell. That makes it
unconditional in effect, and its pose is on screen at the compared frame. The
exploration pack was discarded; both paths below start again from clean
copies.

### (a) A stroke on the `paint` layer of `usr003.ora`, exported flat

**The paint program's part, done programmatically.** The paint program itself
is F12.11 (2)'s subject (F14.8), not this row's.

1. `kit/sheets/usr003.ora` opened with `zipfile`. The layer was found **by
   name**, the one `<layer name="paint">` in `stack.xml` (`data/paint.png`,
   256x580, asserted fully transparent), never by position.
2. A stroke was drawn on it in one opaque colour, RGBA `(32, 224, 96, 255)`,
   inside cell 3: a filled rectangle over sheet pixels x 9–22, y 47–57
   (14x11), plus an 11-pixel diagonal line from (24, 69) to (34, 59). That is
   165 pixels in all, bbox `(9, 47)`–`(34, 69)`. The stroke is deliberately
   off the 4-pixel grid, so it tests HD pixels, not upscaled NES pixels.
3. The `.ora` was re-saved with every other member copied byte for byte, in the
   same order and compression, and `mergedimage.png` regenerated as a paint
   program's save would.
4. **Flat export over the F12.4 name.** The layers whose `visibility` is
   `visible` — `orig`, then `paint` — were composited bottom to top with
   `svg:src-over` at each layer's `opacity` (1.0). `guides` and `palettes` are
   hidden and were excluded. The result was written as an RGBA PNG over
   `<kit-copy>/sheets/usr003.png`; `asset_names.require_asset_name` accepts
   `usr003.png`. As a sanity check, the same composite of the **unpainted**
   `.ora` is byte-for-byte the kit's `usr003.png`. The painted export differs
   from it in exactly 165 pixels, bbox `(9, 47)`–`(34, 69)`.

**Build.** The recording was copied, the kit's `sheets/*.png` and `*.json` were
dropped in (the painted kit copy for `proj-a`, the clean kit for the control
`proj-ctrl`), and `mep_build.py build` ran on each
(`docs/remastering-a-game.md` §5). Both builds: 0 errors (17 warnings, all
the tool's own sheet-size note), 493 tiles, 17 images; `mep_lint.py` on
`proj-a` 0 errors. **`textures/hires.txt` is byte-identical between the
two builds** (sha256 `c663fcca…90fb`), and the only file that differs is
`sheets/usr003.png`, by 165 pixels. So the repaint needs no manifest change,
which is what ADR-0212 requires for a reload.

**Unchanged cells dropped.** `mep_build._EditedProbe`, the rule ADR-0220 §5
names as the return path's filter (the PRD row's wording says

## 5. Found: a kit figure's import re-points keys, so the reload shows nothing

The figure loop `docs/remastering-a-game.md` §4 documents is *import → build →
HD Packs > Reload Repainted Images*. It **does not reach the running game** when
the figure's source sheet is not the sheet that owns the key in the running
pack's manifest. That is always the case for the kit's own figures:
`figures/usr00N-figure.json` maps every cell to `sprites.json`, while in the
built kit project the untouched `usr00N` row owns the key.

Reproduction (kit project `proj-ctrl` as above):

1. Copy `kit/figures/usr003-figure.*`, paint cell `(2, 8)` (the torso key),
   `mep_figure.py import <proj> usr003-figure.png --verify` → `1 painted, 1
   written`, writes `sheets/sprites.png`, `verify: … 0 lost, 0 added: PASS`.
2. `mep_build.py build` → the painted `sprites.png` cell now claims the key
   ("painted beats untouched"). `hires.txt` **changes**: `sheets/sprites.png`
   becomes a new `<img>` (17 → 18 images) and three rules move off
   `usr003.png` (plain 29 → 28, conditioned 52 → 50).
   `mep_figure.py export … pose001` gives the same result.
3. In game, the same way as §4: painted-from-start `0x06DC9F9A` (the stroke
   shows); started on the unpainted pack with `sprites.png` replaced at frame
   3000 and a reload, `0xAB9EB665`, the control's frame. The reload reports `0
   re-decoded … of 17 image(s)`, because the running manifest never loaded
   `sprites.png`.

Expected, by the doc's wording: the reload shows the painted figure. Observed:
nothing changes until the ROM is reopened (ADR-0212's non-goal: a manifest
change needs a reopen). The same holds for painting any kit sheet cell whose
key another sheet owns in the running build: `usr000.png` contributes no
`<img>` to the unpainted build. Path (b) above passes because `spr013` already
owns its key. Filed as #413, not fixed here.

## Reproduction notes

The four scratch helpers (Python 3 with Pillow and numpy; scratch only, not
versioned, following the re-record log's `compare_oam.py` precedent) do
nothing but what is stated above:

- `paint_ora.py <in.ora> <out.ora> <flat.png> 4 40`: §4 (a) steps 1–4.
- `paint_figure.py <figure.png> <tile> <palette> <pack>`: the figure stroke
  of §4 (b).
- `probe_edited.py <project> <sheet>…`: instantiates `mep_build._EditedProbe`
  per sheet and counts `edited(x, y, unit)` over the sidecar's cells.
- `compare.py <control> <reference> <reload> <painted sheet> <unpainted sheet>
  <cellX> <cellY> 32 <screenX> <screenY>`: the tables of §4.
