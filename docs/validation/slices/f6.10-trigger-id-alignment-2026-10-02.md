# F6.10: do patched and unpatched trigger ids align? (ADR-0240 A4 spike, 2026-10-02)

Measurement only. Nothing in the product changed; no ROM, patch or ROM-derived
audio is in the repo. The user's go-ahead for the spike, quoted verbatim:
"go-ahead com 3" (2026-10-02); it is also in ADR-0240's Status line.

## Verdict

**The ids align on the one pack where the measurement could be completed.**
On Mega Man (USA) with the pack's "Music Remixed" patch, the trigger id the
extract-audio tool fires on the unpatched ROM (`JSR $9003`, `A=id`) is the
same id the patched ROM turns into a `$4105` album/track write:
`track = 2*id + 1`, for 17 of 17 pack `<bgm>` lines, with album 0 (`$4104` is
never written). A per-pack name map `ref -> trigger id` is therefore
derivable for this pack **from the patched run alone**, with no hand-listening.

**The full A4 join is not yet derivable.** The second half of the join,
trigger id -> fingerprint id in `fingerprints.json`, does not exist: the
recorder's track ids (`track01..`, `sfx01..`) carry no trigger id, and the
emission order drifts. See "What does not hold".

## Method

1. **Unpatched run** (stock tool, unmodified):

   ```
   ~/Library/Application Support/MesenCE/Tools/spike_sound_driver \
     "<Mega Man (1987) (Capcom).nes>" <work> <out> 48 3 3.0 600
   ```

   Result (`enumeration.log`): tick `$9000`, `trigger: JSR $9003 with A=id`,
   48 ids: 20 bgm, 17 sfx, 11 short; bgm ids are 0-17, 35, 36.
2. **Patched run**: a scratch copy of `scripts/spike_sound_driver.cpp`
   (kept outside the repo, not committed) with two additions: (a) apply an
   `.ips` to the private ROM copy (`SPIKE_PATCH`), (b) skip phases A/B and
   reuse the unpatched run's trigger (`SPIKE_TRIG=J:9003:A SPIKE_P=9000`), and
   per id: reload the title state, stop at the tick, hijack the CPU into the
   trigger with `A=id` exactly as `playFrom` does, then record every CPU write
   to `$4100-$4106` for 3 s of emulated time (write breakpoint; value taken
   from the register of the store opcode at the break). A no-trigger baseline
   run records the title's own writes.

   ```
   SPIKE_PATCH="<HdPacks>/Mega Man (1987) (Capcom)/Customization/Patch - Music Remixed, No Pause/Megaman - Super.ips" \
   SPIKE_TRIG=J:9003:A SPIKE_P=9000 pass2 "<rom>" <work> <out> 48 3 3.0 900
   ```

   The IPS applies by the pack's own `<patch>` hash rule: the library ROM's
   whole-file SHA1 `2F88381557339A14C20428455F6991C1EB902C99` is the first
   `<patch>` key in the pack's `hires.txt`. Applied: 378 records, ROM
   131088 bytes; the patched PRG contains `8E 05 41`, `8D 00 41`, `8D 02 41`
   at file offset `0x13E74` (`STX $4105`, `STA $4100`, `STA $4102`), which the
   stock ROM does not.
3. Both tools were linked against
   `~/VSCodeProjects/MesenCE/InteropDLL/obj.osx-arm64/MesenCore.dylib`
   (the main checkout's build, read only; the commit it was built from was not
   recorded).

Numbers:

- 17 of 17 `<bgm>` tracks of the pack (1, 3, ..., 33) are reached by exactly
  one trigger id (100 %); the two Fireman lines are ids 6 and 7, whose
  unpatched enumerations both open `T71 T69` and are the only two with ~390
  audible frames, as two files for one stage would be.
- 17 of 17 ids that write `$4105` were classified `bgm` by the unpatched run
  (100 % kind agreement); 0 of 28 unpatched `sfx`/`short` ids write anything.
- 17 of 20 unpatched `bgm` ids (85 %) have a patched track. Ids 17, 35, 36
  have none (the patch does not redirect them; not investigated why).

Control: with the pack's default root patch (`Megaman - Super.ips`, byte-equal
to "Patch - Music NES, No Pause (Default)"), the same 48-id patched run
recorded **0 writes** to `$4100-$4106` for every id and the ROM has no
`8x xx 41` stores. Only the "Remixed" patches route music to the pack's OGG.
That control run was observed in the session and not saved.

## Second ROM: Castlevania (inconclusive, not counted)

Unpatched: tick `$838A`, `JSR $8187 A=id`, 48 ids, 10 bgm (ids 38-47), 28 sfx.
The installed `akuogg.ips` is keyed in `hires.txt` to three SHA1s
(`a5081812...`, `a31b8bd5...`, `0d6e5910...`), none of which is the library
ROM's whole-file SHA1 (`7A20C44F...`) or its No-Intro SHA1 (`3DCB69A8...`, the
one the catalog row lists). The host would not apply this patch to this ROM.
It was applied by force anyway (4 IPS records) and gave `$4105` writes for
ids 39, 40, 42, 43, 45, 46 with values 20, 23, 29, 32, 38, 41, i.e.
`track = 3*id - 97` on all six; the pack's `<bgm>` numbers are 20, 29, 38, ...,
so only the values 20, 29, 38 are pack tracks. Ids 38, 41, 44, 47 wrote
nothing; ids above 47 were not run. Because the patch is for another revision
this is not evidence for or against alignment.

Also: the catalog row (`rom.sha1 EE09B857...`) and the locally installed pack
disagree on which ROM hash the Castlevania patch is for.

Metroid (patch hash matches the library ROM): the unmodified tool reports
`no validated trigger (best score 0)` after testing `JSR $C1A3` with A and X,
so there are no ids to align. Zelda was not run.

## What does not hold

1. **No trigger id on the fingerprint side.** `fingerprints.json` tracks are
   `track01..track17` (bgm) and `sfx01..sfx34`; there is no id or hash that
   links one to `enumeration.log`. For Mega Man the recorder wrote 17 bgm
   tracks for 20 enumerated bgm ids (51 tracks in all: 17 bgm and 34 sfx), and an `sfx07` sits between `track11` and `track12`, so the
   emission order is not the id order.
2. A first-onset comparison (note offsets of the first 3 onsets of each id
   against the track's frame-0 events) matched only ids 1 (`track02`), 5
   (`track05`) and 16 (`track14`) uniquely. Ids 1 and 5 imply a shift of 1 and
   0, id 16 a shift of 2: the ordinal join is not usable as-is.
3. The names come from the pack's `hires.txt`, not from the ROM. The measurement
   shows that the patch maps id k to `<bgm>` track 2k+1; whether
   `MUS_RM_Fireman.ogg` really is the song the ROM plays for id 6 rests on the
   pack author, and was not checked by ear. The `.ogg` files are not installed
   locally.
4. One game with a validating trigger and a patch keyed to the library ROM.
   Castlevania is inconclusive, Metroid has no trigger, Zelda untested.

## What this means for ADR-0240 A4 (not decided here)

- Half of A4 is demonstrated: patched `$4105` writes can be harvested per
  trigger id with the existing debugger machinery, giving the `ref -> id`
  table.
- The other half needs a new key: the tool would have to log, per enumerated
  id, the recorder track id it produced (or write the id into the
  fingerprint), because order and note offsets do not recover it.
- The harvest only works for patches that call the same trigger routine with
  the same register convention as the stock driver (true for Mega Man, `P` and
  the trigger address are identical in both ROMs) and only when the host would
  apply the patch to the user's ROM (Castlevania shows a catalog/pack hash
  disagreement that must be resolved first).
- ADR-0240 Option 2 (opt-in generation job) and the PRD F6.10 stop condition
  remain unchanged; the PRD records the completed spike in its delivery
  record.
