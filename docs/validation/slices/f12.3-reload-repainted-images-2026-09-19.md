# F12.3 — reload repainted pack images without reopening the ROM (2026-09-19)

Scope and stop rule live in the PRD (Part A §4, Phase 12, row F12.3) and the
decision in ADR-0212. The stop rule: *a PNG overwritten on disk renders
pixel-exact in a `headless_record` screenshot after the reload, with no state
loss.* This log is the evidence for it, plus the cost measurement ADR-0212 §6
requires before any doc quotes a number.

## 1. The stop rule: pixel-exact after the reload

Three runs, identical except for when the new PNGs reach the disk. `A` is the
control, `C` is the reference (the repaint is already on disk at load), and `B`
is the one under test: the original pack loads, and at emulated frame 2 400 the
run overwrites all 19 `chr/*.png` and asks for a reload.

| run | pack at load | reload | final-frame checksum |
|---|---|---|---|
| A — control | original | none | `0xDBA93B36` |
| B — **reload under test** | original, repainted at frame 2 403 | requested | **`0xA8693E63`** |
| C — reference | already repainted | none | **`0xA8693E63`** |

**B equals C exactly and differs from A.** The frame a repaint-then-reload
produces is byte-identical to the frame the same repaint produces when it was
there from the start, which is the stop rule.

No state was lost: all three runs park on frame 4 808 having played the same
input, and B's frame matching C's is itself the proof — a run whose emulation
had diverged could not land on the same pixels.

The `replace=` and `reload-at-frame=` flags make this deterministic. The
overwrite and the request happen in that order inside the same tick, so nothing
races an outside script. **The trigger counts emulated frames, not wall
seconds**: 80 emulated seconds finish in about 11 wall seconds on this host, so
a first attempt with `reload-at=40` (seconds) never fired at all.

## 2. Cost

The number that matters is what the emulation thread pays: the decode-thread
drain plus the re-decode plus the tile re-cut, all inside one
`OnBeforeSendFrame`.

| what changed | images re-decoded | tile rules re-cut | reported cost |
|---|---|---|---|
| nothing (26 images stat'ed) | 0 | 0 | **0 ms** |
| one sheet (`Chr_0.png`) | 1 | 264 | **2 ms** |
| all 19 `chr/*.png` | 19 | 2 420 | **25 ms** |

A frame budget is 16.7 ms, so the artist's real case — save one file, ask for
it back — costs about an eighth of a frame, and even repainting the whole pack
at once costs about a frame and a half, once, on an explicit action. ADR-0212
predicted "tens of milliseconds" for a single sheet and was pessimistic by an
order of magnitude; the 50 ms/image average F12.1 measured was decode under
contention with 271 images in flight, not a single warm file.

The no-op row is the one that justifies the stat fingerprint: an unchanged pack
costs one `stat` per image and **0 ms**, and its final frame is `0xDBA93B36` —
identical to the control, i.e. a reload that finds nothing changes nothing.

## 3. A resized canvas is refused, and the old pixels survive

`Chr_0.png` (512×512) was replaced mid-run by a 256×256 file.

```
[MEP] reload: chr/Chr_0.png changed size (512x512 -> 256x256) - reopen the ROM to pick it up
[MEP] reload: 0 re-decoded, 1 refused, 0 failed, of 26 image(s), 0 tile rule(s) re-cut, in 1 ms
```

Final-frame checksum `0xDBA93B36` — the control's. The refusal is not a
best-effort partial apply: the image keeps the pixels it had, no tile is re-cut,
and the run is unaffected. This is ADR-0212 §4, and it exists because
`HdPackTileInfo` caches `x/y/w/h` from the manifest and would read a smaller
canvas out of bounds.

## 4. The finding that changed the implementation

The first working build re-decoded the images correctly — the log said
`19 re-decoded, 0 refused, 0 failed` — and **the screen did not change**:
checksum `0xDBA93B36`, the control's.

ADR-0212 §1's claim that an in-place decode invalidates nothing is true of
*pointers* and was incomplete about *caches*. `HdPackTileInfo::Init()` memcpys
its crop out of `Bitmap->PixelData` into its own `HdTileData` and is guarded by
`_needInit`, so once a tile has been cut it never looks at the bitmap again.
Re-decoding the image alone is invisible to every tile already drawn.

The fix is in the same sweep: collect the `HdPackBitmapInfo*` that were actually
re-decoded, then walk `Tiles` once and call `InvalidateCachedPixels()` on those
whose `Bitmap` is in the set. `<background>` images needed nothing —
`HdBackgroundInfo::data()` reads `Data->PixelData.data()` straight through.

The sweep now reports the second number too, which is what `2 420 tile rule(s)
re-cut` above is. ADR-0212 §1 has been amended to say this rather than leave the
next reader with the same wrong mental model.

## Honest limits

- **One pack, one ROM, one host.** Zelda's 26 images and 2 171 rules against
  Metroid's 271 images and 150 199 rules: the tile-invalidation walk is linear
  in `Tiles`, so the Metroid case is expected to cost more than the 25 ms
  measured here and **has not been measured**. The walk only runs when something
  was re-decoded, so the no-op cost stays flat.
- **The repaint is synthetic.** Solid-colour PNGs of the right size prove the
  pixel path, not that a real `.psd` export round-trips. That is F12.4's
  subject.
- **CHR RAM only.** Zelda is a CHR RAM game. Nothing in the reload path reads
  the CHR form, but a CHR ROM pack was not run.
- **Not measured: the GUI path.** The menu action (`Reload Repainted Images`)
  calls the same interop entry point the headless flag does, and the UI builds,
  but no human has clicked it. Everything above is headless.
- **Not measured: the drain by itself.** The reported milliseconds cover
  `WaitForAsyncFrameDecode` plus the decode plus the re-cut as one number. The
  0 ms no-op row bounds the drain plus 26 stats at under half a millisecond,
  which is why it was not split further.
- **Not measured: a manifest change.** Out of scope by ADR-0212's non-goal; a
  `hires.txt` edit still needs the ROM reopened, and nothing here checks what
  happens if someone tries.

## Reproduction

```sh
make capture-tool        # CLT make + CLT clang++, per CLAUDE.md
# <work>/<run>/mesen-home/HdPacks/<rom name>/  <- the pack
# <work>/<run>/rom/<rom name>.nes              <- the ROM, no sibling mep/
scripts/headless_record <rom> 80 <work>/<run>/out capture mep-off \
  input=<work>/full.txt reload-at-frame=2400 \
  replace=<pack>/chr/Chr_0.png=<repainted>/Chr_0.png
```

`replace=` may be repeated. The `[MEP] reload:` lines are in
`<work>/<run>/mesen-home/mesen.log`; the frame checksum is on stdout
(`capture: ... checksum=`).
