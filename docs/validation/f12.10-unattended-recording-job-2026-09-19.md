# F12.10 — unattended recording job, one row per ROM (2026-09-19)

Scope and stop rule live in the PRD (Part A §4, Phase 12, row F12.10). The stop
rule, in full: *the job completes end to end with no interactive step, every
produced kit reports `--verify` 0 errors, `library-report.md` names the driver
per ROM, and the SMB row says `static` while the two others say `routes`.
Failure of one ROM is a row, not an abort.*

All four hold. What follows is the evidence, plus two things the row assumed
that turned out not to be true of a real checkout.

## Inputs

- **Three ROMs**, the bounded input the row names: `roms/Mega Man 3 (USA).nes`
  and `roms/Zelda.nes` from the working checkout (both have route sets under
  `scripts/stages/`), and `Super Mario Bros. (1985) (Nintendo).nes` from the
  user's library (no route set; exercises path (d)).
- **A `.bk2` beside them**, `.cache/tas/zelda-allitems.bk2`, whose header hash
  is this Zelda dump — put there on purpose so driver precedence is *observed*
  rather than asserted.
- `scripts/headless_record` sha256
  `97378201f3f8beb882c929af30d70acaaf77e734aeaccba58bb6bf3de63c2261`. F12.10
  changes no Core code; this is the same binary F12.3 and F12.4 were measured
  with.
- Host: MacBookAir10,1 / Apple M1, 8 cores, 16 GB, macOS 26.6.2.

`scripts/record_library.sh <roms-dir> <out-dir> 60`, **83 s wall** for the whole
job: 5 recordings of 60 emulated seconds each (one minted state and two stages
per route-driven ROM), plus three kit generators per ROM. Headless runs far
faster than real time, which is why 300 emulated seconds cost 83 s of clock.

## The report

| ROM | driver | status | stages | retained frames | seen % | figures | scenery | maps | kit `--verify` |
|---|---|---|---|---|---|---|---|---|---|
| Mega Man 3 (USA) | `routes` | recorded (1 state minted) | 2 | 6 891 | 23.5 | 12 | 5 | - | **0** |
| Super Mario Bros. (1985) | `static` | no kit — static path needs F12.9, which is not shipped | - | - | - | - | - | - | - |
| Zelda | `routes` | recorded (1 state minted) | 2 | 4 416 | 83.4 | 4 | 1 | - | **0** |

Every `--verify` that ran reported 0 errors — three parts per kit (`chr`,
`sprites`, `background`), all six `ran: true, errors: 0`.

**Driver precedence is observed, not assumed.** Zelda's row reads *"route set
zelda/ declares this No-Intro SHA1; 2 recordable stage(s); a movie also matched
(zelda-allitems.bk2) and (a) wins"*. Both (a) and (b) were available for the
same ROM in the same run, and (a) took it.

`maps` is `-` for every row by design: a panorama needs a per-stage
`MESEN_SHEET_GRID_DUMP`, and one Contra route's dump is ~190 MB. A library job
that wrote one per stage would produce gigabytes for a surface it does not
otherwise use, so `scripts/artist_map.py` stays a tool you point at a run. The
report says this in its own body rather than leaving a blank column.

## Two things the row assumed that a real checkout does not have

### 1. No `.mss` save state is versioned — measured, not supposed

`.gitignore` says it plainly (*"None of that is ever versioned (`.mss` is a save
state…"*), because a CHR RAM state carries the game's graphics. So a checkout
holds a route set's **scripts** and none of the **states** those scripts start
from, and `record_stages.sh` falls back to power-on when a state is missing.

The first run of this job did exactly that, and the result is the reason the
job now mints:

| | before minting | after minting |
|---|---|---|
| Mega Man 3, retained frames | **2** (1 per stage) | **6 891** |
| Mega Man 3, figure sheets | 0 — `artist_kit` refused the pack | **12** |

Two retained frames is a title screen. `artist_kit.py` refused it outright
(*"no usable sheets/poses.json"*), which is the tool behaving correctly and is
also why this was caught rather than shipped as a low number.

The job now mints every state its route set needs, into **its own copy** of the
stage folder under the output directory — the repository tree is never written
to. The mint→stage pairing is the rule `scripts/stages/README.md` documents by
example: a mint's state is named for the stage that will use it, one mint may
serve several stages, and the most specific mint wins (`stage1-water` takes
`mint-stage1-water`, not `mint-stage1`). That pairing lives in
`library_job.mint_plan` so it is unit-tested rather than buried in shell.

It does not solve everything, and the job says so: Contra's nine later stages
have no mint at all — their states come from a `.chain.txt` that
`replay_chain.sh` replays, which this job does not do. `mint_plan` reports them
as **unserved** instead of recording a title screen and calling it a stage.

### 2. A route set did not say which ROM it was authored against

The row says a set is "matched by hash", and nothing in `scripts/stages/`
carried a hash. Matching by folder name was available and was **not** used:
guessing that `zelda/` means the Zelda in hand is how a pack gets recorded
against the wrong ROM — that is issue #314's shape exactly.

So a set now declares its dump in `scripts/stages/<game>/stage-set.json`, and a
set without one never matches and is listed in the plan as undeclared. **Only
two are declared** — `mm3` and `zelda` — because those are the two this run
actually verified. `contra`, `excitebike`, `metroid` and `zelda2` are left
undeclared rather than filled in with hashes nobody has run a route against.
Declaring one is one line and one verifying run; claiming one is not.

## Honest limits

- **Three ROMs, one console.** NES only, one CHR ROM game and one CHR RAM game
  recorded, one ROM skipped. Nothing here says how the job behaves on a
  thirty-ROM library, and the `find_roms` one-level rule is asserted by the
  unit suite rather than by a large run.
- **Path (d) produces nothing.** The row's prerequisite is F12.9 (static kit
  from the ROM alone), which is not shipped and needs an ADR amending
  ADR-0183 §1. SMB's row says `static` as the stop rule requires, and its status
  says the kit is absent and why. The job is complete for (a), (b) and (c); (d)
  is a resolved driver with no implementation behind it, and that is the one
  part of this slice left undone.
- **Path (b) was never executed, only resolved.** The only `.bk2` in hand for a
  ROM we have is the Zelda one, and (a) legitimately outranks it. The movie
  branch of the shell is therefore unexercised by this run; the *matching* is
  covered by the unit suite, including the case that matters — a bk2 carrying a
  No-Intro hash is refused, because a bk2 header names the **whole file**
  (`scripts/fm2_to_bk2.py`, `rom_hashes`) and accepting the wrong one would run
  a movie against a dump it was not recorded on.
- **`seen %` is a coverage number, not a quality number.** Zelda's 83.4 % and
  Mega Man 3's 23.5 % are the share of *cells on surfaces the run saw*; they say
  how much of the kit has evidence behind it, not how good the recording is.
- **No route set declares an ADR-0182 mechanism list**, so the report's
  mechanism section says so rather than implying coverage. Writing those lists
  is a human job on each set.

## What the automated suite covers

`python3 scripts/test_library_job.py` — **22/22**, wired into `make doc-checks`.
Synthetic iNES files and script folders in a temp dir; no emulator, no ROM. The
two cases that exist because the first real run got them wrong are named as
such in the file: minting, and the whole-file-vs-No-Intro hash.

## Reproduction

```sh
make capture-tool                      # once
scripts/record_library.sh <roms-dir> <out-dir> 60
```

`<out-dir>/library-report.md` is the report; `plan.json` is what the resolver
decided before anything ran, and `results.json` is appended after each ROM, so a
job that dies on ROM six still leaves the five rows it earned.
