# F12.12 — a third-party pack read as an index of facts about the ROM (2026-09-20)

The slice shipped in `0a14dae1` (`scripts/mep_import.py index`, ADR-0210 §3)
with unit coverage but no measurement against a real pack. This log is that
measurement, on the two packs ADR-0210 names: one CHR RAM game, where the
index is the only static source of shape, and one CHR ROM game, where it can
only be palettes. Both inputs come from `docs/community-packs.json`, both were
downloaded fresh, and both content hashes match the catalog row byte for byte.

It closes the row — and it retracts one of ADR-0210's own Context figures.

## Contra — CHR RAM, the index is a real gain

```
python3 scripts/mep_import.py index <contra80s>/hires.txt \
    --pack <our contra pack> --rom "Contra (1988) (Konami).nes" --report contra-index.json
```

| quantity | value |
|---|---|
| their rules / `<ver>` / keying | 13 218 · 106 · 32-hex pattern data |
| their distinct shapes | 3 404 |
| our recorded shapes | 2 138 |
| their rules already covered by ours | 3 735 |
| **cells rendered from their pattern bytes** | **2 583** |
| keys once the sheet is built | 6 166 |
| palettes in the sheet | 131 |
| conditioned rules contributing a bare key | 1 364 |
| wall time | **0.93 s** |

ADR-0210's prospective figure for this pair was **+2 585**; the shipped path
renders **2 583**, a difference of two shapes (0.08%). The shipped number is
the one that counts, and the order of gain the decision was taken on holds:
a recording that saw 2 138 shapes gains 2 583 more from the pack's own pattern
bytes, which are the game's art, rendered by us through the recorded path.

`<condition>` lines were read for none of it: the 1 364 conditioned rules
contributed the bare key of the tile they name and nothing else, which is
ADR-0210 §3's refusal working as written.

## Ninja Gaiden — CHR ROM, palettes only, and nothing dropped

```
python3 scripts/mep_import.py index <ninja gaiden>/hires.txt \
    --pack <our ng pack> --rom "Ninja Gaiden (1989) (Tecmo).nes" --report ng-index.json
```

| quantity | value |
|---|---|
| their rules / `<ver>` / keying | 19 153 · 100 · tile index |
| shapes taken | **0** — the shape half of every key is discarded |
| rules naming a tile this dump has | **19 153 of 19 153** |
| **rules dropped as out of range** | **0** |
| palettes taken | **401** (our recording has 19) |
| sheet written | none |
| wall time | **0.16 s** |

The shape count is 0 by construction and that is the decision working: for a
CHR ROM game `artist_chr_kit.py` already publishes the ROM's CHR whole, so a
third party cannot add a shape. What it adds is the palette set, and 401
against our recording's 19 is the whole of its contribution.

### The retraction: nothing is out of range

The expected result for this run was **5 532 keys dropped as out of range**,
from ADR-0210's Context item 2. It does not reproduce, and the ADR is the thing
that is wrong.

That pack is `<ver>100`. `HdPackLoader::ReadTileData` reads the tile token as
**decimal** below `<ver>103` and as hex from 103 on, and `Rule.parsed_index`
branches on `<ver>` for exactly that reason. Read both ways over the same
19 153 rules:

| reading | distinct indices | max | ≥ 8 192 |
|---|---|---|---|
| decimal (the loader's, `<ver>100`) | 7 382 | **8 190** | **0** |
| hex (unconditional) | 7 382 | 33 168 | 5 532 |

8 190 is inside the dump's 8 192 tiles. The "33 168" and the "5 532" in
ADR-0210 are a base-16 reading of decimal tokens, and the ADR's last
Consequences bullet prescribed that very reading ("normalise the index
(`int(field, 16)`)") while warning about two neighbouring traps.

What this does **not** overturn:

- **The filter.** It is mandatory, it is implemented, and it is what made the
  discrepancy visible at all — the run reports its range accounting whether or
  not it drops anything.
- **The decision.** A CHR ROM game takes palettes only; a CHR RAM game takes
  the pattern bytes. Both halves measured above.
- **The wrong-ROM case.** A pack aimed at a dump we do not hold is still real
  and still the reason the filter exists. The Ninja Gaiden pack simply is not
  an instance of it: it declares our sha1 and addresses our tiles.

ADR-0210 was amended the same day — Context item 2 retracted with these
numbers, the Consequences bullet corrected to "branch on `<ver>`", Decision
untouched.

## What this does not deliver

- **No run-time measurement.** Neither read was installed and rendered; the
  claim measured here is what the index yields, not what it changes on screen.
  For Contra the sheet is an editing surface, and ADR-0183 §3 marks every cell
  `seen: false` precisely because nothing observed it.
- **The palette comparison is against these recordings, not against a
  best-effort one.** ADR-0210 quotes "401 to our 364" for this pair; our
  Ninja Gaiden pack here is a short F12.2 sweep recording with 19 palettes, so
  the ratio is flattering. The direction is the ADR's point and is unaffected;
  the magnitude depends on how much play the recording saw.
- **No `<patch>` pack was exercised.** Neither input carries `<patch>`, so
  ADR-0210's second mandatory filter is still covered only by unit tests.

## Reproduce

```
curl -sSL -o Contra80s.zip https://github.com/TasticHacks/Contra80s/releases/download/1.1/Contra80s.zip
python3 scripts/mep_import.py index "<unzipped>/Contra (U) [!]/hires.txt" \
    --pack <our contra pack> --rom <contra>.nes --report contra-index.json
python3 scripts/mep_import.py index "<unzipped>/Ninja Gaiden (USA)/hires.txt" \
    --pack <our ng pack> --rom <ng>.nes --report ng-index.json
```

`--report` is the durable trace: a CHR ROM run writes no sheet, so the JSON is
the only record that the read happened and what it dropped.
