## 3. Stop condition (3) — pixel-exact reach into the game

### 3.1 A `headless_record` usage bug invalidated the first round of attempts

`scripts/headless_record <rom> <seconds> <output-prefix> ...` computes its
sandbox home as `parent_path(<output-prefix>)/mesen-home`
(`scripts/headless_record.cpp:836-837`), **not** `<output-prefix>/mesen-home`.
Passing a bare directory as the prefix (e.g. `.../run/A0`) makes `home`
resolve to that directory's *parent* — so several runs meant to use distinct
sandboxes (`A0` unpainted, `C` painted-from-start, plus an
`EnhancementPacks/`-based attempt) were **silently sharing one empty home
directory** the whole time, which is why every configuration, including a
"vanilla, no pack installed at all" control, produced the identical
checksum `0x41886205` and no `mesen.log` — none of them had actually found a
pack. This is a reproducible trap for anyone invoking `headless_record` with
a directory instead of a `.../out`-style file prefix; worth a doc note or a
guard in the tool itself (out of scope here, not filed as a bug since it's a
usage error rather than incorrect behavior, but flagged for whoever owns the
tool's help text).

Also found and fixed along the way: `mep_build.py`'s default pack layout
nests `hires.txt` under a `textures/` envelope (`pack/textures/hires.txt`,
the MEP layout per ADR-0005). The **legacy** `HdPacks/<rom>/` loader
(`HdPackLoader::HasLoosePack`, `Core/NES/HdPacks/HdPackLoader.cpp:72-76`)
looks for `HdPacks/<rom>/hires.txt` directly — no `textures/` level. F12.3's
own log installs the pack by copying `auto/textures/*` up to
`HdPacks/<rom>/` directly (its `replace=<pack>/chr/Chr_0.png=...` path has no
`textures/` prefix); the same flattening was needed here.

With both fixed (correct `<prefix>/out` argument, `textures/*` flattened
into `HdPacks/<rom>/`), the pack loads correctly:

```
[MEP] textures: loaded loose NES HD pack from HdPacks/Contra (1988) (Konami)/hires.txt (568 tiles, scale 4)
[MEP] LoadHdPack: 9 ms; tiles=568 keys=250 images=22 backgrounds=3
[MEP] LoadAsync (bitmap decode): 48 ms, 25 image(s)
```

and the capture resolution changed from `256x240` (no HD render) to
`1024x960` (4x upscale, HD render active) — independent confirmation the
pack is genuinely in effect. The load log also surfaced three unrelated,
pre-existing `<background>`-over-`<tile>` precedence notices (ADR-0050/
ADR-0156) for `screen001/2/3` — expected precedence behavior, not a defect.

### 3.2 The chosen cell was a poor pick for a final-frame-only proof

The painted cell (sheet `usr000`, index 1, canvas rect x=76,y=4,w=32,h=32)
turned out to be governed by a composite/adjacency-gated rule
(`[spr002_n5]<tile>19,000080808187808D...,FF36160F,76,4,...` —
`spriteNearby`), with a plain fallback rule for the same key also present.
Direct pixel diff of the two packs' installed `usr000.png` confirmed the
paint reached disk correctly (exactly 1024 differing pixels, bbox
`(76,4)-(107,35)`, matching the intended cell exactly).

`headless_record capture` only reads the **final** frame of a run. Scanning
final-frame checksums across `seconds=5,10,...,60` on the same mint state +
`stage1-long.txt` route showed **A (unpainted) == C (painted) at every
sampled endpoint**, but the checksums for `seconds>=20` repeat exactly
(`0x8658DE07` at 20/35/45, `0xF91E520C` at 25/30/40/50/55) — the route's tail
settles into a short repeating idle cycle once the input script runs out,
and this specific composite pose (recorded 146 times somewhere across the
full 5410-frame capture) never lands on one of the handful of endpoints
sampled. That is a sampling gap, not evidence the mechanism doesn't work —
the on-disk pixel diff and the pack-load log both independently confirm the
paint and the pack are correct; only the "does it show up on the one final
frame I happened to check" step came up empty.

**This stop condition is left open**, pending either: (a) picking an
unconditional, non-composite cell for the repaint, or (b) driving the proof
with `reload-at-frame=`/`replace=` at a frame known (from a synctrace or a
denser per-frame scan) to hold the pose, exactly as F12.3 did for its
whole-pack magenta repaint. Both are mechanical follow-ups, not blocked on
anything found in this session.

## 5. Defect (a) — the sheet caption is truncated and overlaps row 0

**Root cause, confirmed still present on this worktree's `main`-based HEAD.**

`scripts/artist_kit.py:386`:

```python
text = f"{grid_title(grid, names)} | {ids}" if r == 0 and names is not None else ids
```

`Names.load()` (`scripts/artist_kit.py:465`) always returns a `Names()`
instance rather than `None` when `--names` is omitted, so the long fallback
caption from `grid_title()` (~line 528, e.g. `"figures no cycle or sequence
ordered — N of them, seen in M frame(s) between them"`) is drawn on **every**
sheet's row 0 unconditionally, regardless of whether a real names file was
given. `scripts/ora_writer.py`'s `draw_text()` (~lines 120-131) has no wrap
or width bound, so the text runs off the canvas edge (silently clipped by
`_fill_rect`'s clamp) rather than wrapping — producing the truncated
appearance. `row_captions()` also places the caption at `y = GUTTER`, the
same y as row 0's cell top, so it overlaps row 0's art instead of sitting in
a reserved caption band.

Empirically confirmed by decoding `usr003.ora`'s `guides` and `orig` layers,
compositing the top 60 canvas rows (guides in red), and viewing the result:
it shows `"FIGURES NO CYCLE OR SEQUENCE ORDERED ? 19 O..."` truncated at the
right edge, directly over row 0's figures — an exact match to the
user-reported GIMP defect.

**Proposed fix (not implemented):** only draw the long fallback caption when
a real `--names` file was actually supplied (check the loaded file's
presence/emptiness rather than `is not None`), and give `row_captions()` a
dedicated caption band above row 0's cell top plus wrapping/truncation with
an ellipsis in `draw_text()` so a caption that is drawn can never overlap
art.

## 6. Defect (b) — the palette swatch band looks like it belongs to the wrong row

**Root cause, confirmed still present; correct data, misleading presentation
— not a wrong-index bug.**

`scripts/compose_engine.py` (~lines 1574-1580):

```python
swatches = ora_writer.nes_swatches(sorted({t.get("palette") for c in cells for t in (c.get("tiles") or []) if ...}))
```

collects every distinct palette **observed anywhere on the whole sheet**
(not per-row/per-cell) and sorts them lexicographically by raw hex string,
with no positional relationship to which row/cell actually uses which
palette. `scripts/ora_writer.py`'s `_palettes_band()` (~lines 332-369) then
draws all of them concatenated into one unlabeled strip aligned to the
sheet's first cell row.

Empirically confirmed on `usr001.ora`: the band's leftmost swatches
(black/white/grey) belong to palette `FF20000F`, used by cells 4/5/6, not
row 0. Cell 0's actual palette `FF36160F` (black/salmon/red) appears later
in the band purely because `"FF20000F" < "FF36160F"` as strings. Every color
shown genuinely was observed somewhere on the sheet — the band isn't wrong,
but it gives no indication which swatch group belongs to which cell/row, so
a viewer naturally (and incorrectly) reads "the swatches nearest row 0" as
row 0's own palette.

**Proposed fix (not implemented):** either draw one palette band per row
(tied to that row's own cells), or keep one sheet-wide band but group/label
swatches per palette with a visible separator, or at minimum order palettes
by first-use cell/row position instead of raw hex string so the leftmost
group corresponds to the sheet's first row.

## 7. GIMP 2.10 OpenRaster importer facts (`file-openraster.py`)

Answered in full to the coordinator mid-session; repeated here for the
record.

1. **Active layer after import**: neither "first `<layer>`" nor "topmost".
   `get_layers()` (lines 254-263) walks `<stack>`'s children with a plain
   `for item in root:`, i.e. stack.xml document order (topmost element
   first, matching how GIMP's own `save_ora` writes `img.layers`
   top-to-bottom). The main loop in `load_ora()` (lines 267-318) calls
   `pdb.gimp_image_insert_layer(img, gimp_layer, parent, layer_no)`
   (lines 309-311) once per layer in that order, with **no explicit
   "set active layer" call anywhere in the file**. GIMP's
   `gimp-image-insert-layer` has the side effect of making the
   just-inserted layer active, so whichever layer is inserted **last**
   ends up active — the **bottommost** layer in our stack.xml (`orig`),
   not the topmost (`paint`).

   **Decision-relevant implication**: moving `paint` to the top of the
   stack (first in document order) would make GIMP insert it *first*, not
   last — it would **not** become the active layer by this mechanism. To
   land on `paint` via this default side effect, `paint` would need to be
   *last* in document order (i.e. the bottommost layer), which conflicts
   with keeping it visually on top. This should be checked before amending
   ADR-0220 on this premise — ideally with an empirical open-in-GIMP test,
   which was not done this session.

2. **Attributes read**: `get_layer_attributes()` (lines 56-67) reads
   exactly `src, name, x, y, opacity, visibility, composite-op`.
   `edit-locked` is never referenced anywhere in the ~396-line file
   (confirmed by a full-file grep). There is no `selected` attribute in
   OpenRaster at all (confirmed independently by ADR-0220 §3's own text),
   so the importer neither reads nor invents one.
