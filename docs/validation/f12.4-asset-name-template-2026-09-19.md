# F12.4 — the painting surface's name is the name the paint program exports to (2026-09-19)

Scope and stop rule live in the PRD (Part A §4, Phase 12, row F12.4) and the
decision in ADR-0213. The stop rule: *saving in the paint program overwrites the
kit PNG and F12.3 renders it*, and it names what we are allowed to measure —
**valid names, reload fired, pixel-exact result**. This log is the evidence for
those three, and nothing more: no artist was watched, no paint program was run.

## 1. Valid names, on the kits rather than on examples

Both kits were re-assembled with the new gate. Every surface was stamped with
its `assetName` and checked against the ADR-0213 rules, per name and per folder.

| kit | surfaces | stamped | invalid | case clashes | folders |
|---|---|---|---|---|---|
| Contra | 33 | 33 | **0** | **0** | `chr/`, `scene/`, `sheets/` |
| Zelda | 396 | 396 | **0** | **0** | `chr/`, `map/`, `scene/`, `sheets/` |

429 real surfaces, all usable by all three readers. That is the honest shape of
this result: **the contract found nothing wrong with what the generators
already write.** It is a guard against the next surface kind and against the
two names that are derived from outside input (`<stage>-NNN.png` and
`pano-<map stem>.png`), not a bug fix — ADR-0213 §Context says so, and the
suite asserts these live names *valid* precisely so the contract cannot drift
into refusing everything.

The Zelda kit's `map` part reports its pre-existing `verify` FAILED line (301
keys added). That is the panorama's own rebuild report, untouched by this
slice, and it is recorded here only so nobody reads its absence as a pass.

## 2. The name is the join

The kit generated from the installed Zelda pack writes 19 surfaces:

```
chr/Chr_0.png  -> assetName Chr_0.png
chr/Chr_10.png -> assetName Chr_10.png
chr/Chr_8.png  -> assetName Chr_8.png
...
```

and the pack's own manifest holds exactly 19 `<img>` targets, `chr/Chr_0.png`
first. **Same names, both sides.** This is what makes a save in the paint
program reach the game: the artist exports to the name the kit gave them, and
that name is the one F12.3's reload stats.

Everything in §3 is driven by `assetName` alone — the file names are read out
of `kit.json` and never typed — so the run fails if that identity does not
hold.

## 3. Reload fired, pixel-exact result

Three runs, same 4 739-frame input (`scripts/stages/zelda/mint-stage1.txt` +
`stage1-run.txt`), same sandbox, all parked on frame 4 808.

The "save" is performed on the **kit's** surfaces, in place, under their own
names: each `<kit>/chr/<assetName>` is read, every opaque pixel inverted, and
written back over the same path. Then the painted file is copied onto the pack
by `assetName`, which is the artist's export step.

| run | pack at load | reload | final-frame checksum |
|---|---|---|---|
| A — control | original | none | `0x55645B9C` |
| A2 — control, repeated | original | none | `0x55645B9C` |
| B — **under test** | original, painted at frame 2 400 | requested | **`0xC4D2F4DD`** |
| C — reference | already painted | none | **`0xC4D2F4DD`** |

**B equals C exactly and both differ from A.** A painted kit surface, copied
onto the pack under the name the kit published, renders byte-identically to the
same paint applied before the ROM was ever loaded.

The reload fired and said so:

```
[MEP] reload: 19 re-decoded, 0 refused, 0 failed, of 26 image(s), 2420 tile rule(s) re-cut, in 25 ms
```

`A`'s log contains no `[MEP] reload:` line at all, which is the negative
control for "reload fired".

**On the control's value.** A is `0x55645B9C` here and was `0xDBA93B36` in the
F12.3 log of the same day, on the same binaries. The sandbox was copied from
that run's home rather than minted fresh, so its persisted settings are not
identical. A and A2 — two runs from two separate copies of that baseline —
produce the same checksum, so the run is deterministic and the A/B/C comparison
is sound; the number is simply not comparable across the two logs, and quoting
it as if it were would be wrong.

## Honest limits

- **No paint program was run.** The save is a scripted inversion of the kit's
  own PNG. It proves the kit's file round-trips through our reader and writer
  and lands under its name; it does not prove Photoshop's generator, GIMP's
  *Overwrite* or Aseprite's *Repeat last export* behave as
  `docs/remastering-a-game.md` says. Those four rows are read off each
  program's documented behaviour and are **unverified here**. This is the row a
  person has to log, and this phase's cold-read rule is the place it belongs.
- **Photoshop's `-assets` folder is stated, not solved** (ADR-0213 §4). A
  Photoshop user copies one folder. Nothing in this log measures that copy.
- **One console, one pack kind.** The render half ran on a CHR RAM NES game
  through `chr/` pages. `sheets/`, `scene/` and `map/` surfaces were checked for
  their names on both kits but were not painted and reloaded.
- **`sanitize_asset_stem` was not exercised on real input.** Neither bounded
  kit has a stage id that needs rewriting, so its behaviour here comes from the
  unit suite only. ADR-0213's Consequences already record its known hole (two
  inputs can collapse onto one name).

## Reproduction

```sh
python3 scripts/artist_chr_kit.py <mep-shaped pack> --rom <rom> --out <kit>
python3 scripts/artist_kit_assemble.py <kit>          # stamps assetName, gates the names
# paint <kit>/chr/<assetName> in place, then:
scripts/headless_record <rom> 80 <out> capture mep-off input=<full.txt> \
  reload-at-frame=2400 replace=<pack>/chr/<assetName>=<kit>/chr/<assetName>
```

`replace=` is repeatable. The `[MEP] reload:` lines are in
`<sandbox>/mesen-home/mesen.log`; the frame checksum is on stdout
(`capture: ... checksum=`).
