## Renderer size rounding (MainWindow): held back, then ported

Upstream rounds the physical renderer size up to even numbers and then sets
the control's logical size from those rounded pixels. Both changes break the
fork's headless contract, and at least one assertion fails whichever way the
rule is applied:

- round up to even (upstream): the renderer comes out 376 px tall in a 375 px
  panel, so it overflows the panel (`The_picture_is_letterboxed_inside_the_panel_and_keeps_its_ratio`)
  and no longer matches the shared fit (`The_renderer_is_sized_by_the_shared_fit_rule`,
  `Force_integer_scale_does_not_apply_to_a_normal_window`);
- round down to even inside `RendererViewportFit` (tried): 402x374 misses the
  core's aspect ratio at the 3-decimal precision the letterbox test asserts
  (1.075 vs 1.071);
- device-pixel snap alone: 402.00001 vs the fit's 401.674, whenever the aspect
  gives a fractional width. Which aspect is in effect depends on whether a
  parallel test has a ROM loaded, the same parallelism as #432, so this one
  fails only some of the time.

The merge keeps the fork's sizing (every headless test green) and marks the
held-back lines with a comment in `RendererPanel_LayoutUpdated`. Nothing is
lost on the fork's main platform, because upstream's shaders are Windows + Linux
only and macOS keeps the software renderer. To take the upstream behavior
later: move the even-size rule and the snap into `RendererViewportFit` (P.7
geometry lives there), cover them in `RendererViewportFitTests`, and loosen the
headless assertions to one device pixel.

### Follow-up: ported (2026-09-24)

User's decision, verbatim: "em paralelo, rode o arredondamento do renderer do
upstream". Both upstream rules now live in `UI/Logic/RendererViewportFit.cs`
and `RendererPanel_LayoutUpdated` only consumes them. The rule, with `r` the
core's aspect ratio and `dpi` the layout scale:

- **Even physical size.** `RealWidth` and `RealHeight` are even. Upstream
  rounds up; the fork rounds down, so the picture never overflows the panel:
  `RealWidth <= floor(panelWidth * dpi)`, same for the height. (The one
  exception is inherited: with `FullscreenForceIntegerScale` clamped to 1x on
  a panel shorter than one emulated screen, the picture already overflowed.)
- **Binding axis.** The axis the fit is bound by gets the largest even pixel
  count not above the exact fit in physical pixels. The other axis is the
  even count nearest to `binding * r` (or `binding / r`), allowed up to the
  panel's own even size. If that would still pass the panel, the other axis
  binds instead. Stepping the binding axis down 2 px is the last resort; no
  case in the test sweep needs it.
- **Aspect tolerance.** `min(|W - H*r|, |H - W/r|) <= 1` physical pixel
  (`RendererViewportFit.AspectErrorPixels`). This replaces the old
  "ratio equal to 3 decimals" check, which an even size cannot meet (402x374
  is 1.075 against 1.071).
- **Whole physical pixels.** The logical size is upstream's exact
  expression, `Math.Round(real / dpi, 8, ToZero) + 0.00001`, so
  `Width * dpi` is `RealWidth`. Upstream adds the `1e-5` so a quotient like
  401.99999999 is not laid out a pixel short.
- **Fill.** The degenerate-input fill (unknown aspect ratio, a panel with no
  bounds yet) is snapped the same way.

The 375-px panel that held the port back now gives 498x374 at 4:3. Upstream
would give 376 rows.

No ADR was amended. No ADR defines the P.7 geometry; the contract lived in
this document, the tests and `manual-validation-automation-plan.md`.
