# F14.4 — ADR-0229 option (i) measured on a prototype (2026-09-23)

The measurement ADR-0229 ("What decides it") asks for before it can be
accepted: option (i), where every shape `ProcessTile` draws enters the shape
registry, run on the two recordings ADR-0209 measured (Castlevania 60 s idle,
Zelda 85 s from `scripts/stages/zelda/mint-stage1.txt` + `stage1-run.txt`).
ADR-0229 stays **`proposed`**. This log measures a prototype and records the
numbers. It does not decide anything and it does not ship the change. Raw
material (packs, dumps, logs, scripts) lived in a session scratchpad and is
not versioned. This log keeps the numbers.

## Headline

On these two runs option (i) reaches **no pack key that today's sheets do not
already reach.** The 80–84 % of `hires.txt` that no sheet shows is not made of
shapes the PPU drew and the registry missed. It is the bootstrap's PRG-scan
`defaultTile` export (ADR-0043/ADR-0210): tiles that were **never drawn**
during the recording. Option (i) cannot reach those by construction, since
ADR-0229's non-goals rule them out. Of the shapes that *were* drawn, today's
sheets already reach **100 %** on both games. The drawn *keys* that no sheet
reaches are extra palettes of shapes that are already on a sheet: a cell
carries one palette. Option (i) does not touch that gap.

## The prototype

The diff is 16 added lines. It was not merged (the ADR is `proposed`); it is reproduced here so the run can be repeated:

- `HdPackBuilder.cpp`, `ProcessTile`, new-exact-key branch: one line,
  `RegisterDrawnShape(tile);`. The file goes from 2 427 to **2 428 lines,
  exactly its ADR-0137 ceiling** (`make doc-checks` passes). There is no room
  for a second line.
- `HdPackBuilder.h`: an inline `RegisterDrawnShape` that calls `ShapeIdFor`
  when screen capture is on and the environment variable is set. It is read
  once per process.

It runs once per *new exact key*, not once per pixel, so the hot path adds
one branch on a map miss that already allocates an `HdPackTileInfo`.

```diff
--- a/Core/NES/HdPacks/HdPackBuilder.cpp  (ProcessTile, new-exact-key branch)
 	} else {
+		RegisterDrawnShape(tile); //ADR-0229 (i) measurement prototype, see HdPackBuilder.h
 		CaptureOrCapPaletteVariant(x, y, tileAddr, tile, chrBankHash, transparencyRequired);
 	}
--- a/Core/NES/HdPacks/HdPackBuilder.h  (after ShapeIdFor)
+	void RegisterDrawnShape(const HdPpuTileInfo& tile)
+	{
+		static const bool enabled = std::getenv("MESEN_ADR0229_REGISTER_ALL") != nullptr;
+		if(enabled && _captureScreens) {
+			ShapeIdFor(tile);
+		}
+	}
```

## Commands

```sh
# every run: a fresh sandbox dir holding only a copy of the ROM
export MESEN_SHEET_GRID_DUMP=<dir>/grid-dump.txt MESEN_OAM_STREAM_DUMP=<dir>/oam-dump.txt
[export MESEN_ADR0229_REGISTER_ALL=1]      # "on" arm only

headless_record <dir>/Castlevania.nes 60 <dir>/rec bootstrap hdpack-off log
# Zelda: roms/Zelda.nes (No-Intro SHA1 BE2F5DC8…, the dump stage-set.json pins);
# one power-on run, input = mint-stage1.txt followed by stage1-run.txt (4 739
# frames of script, then idle to 85 s)
headless_record <dir>/Zelda.nes 85 <dir>/rec bootstrap hdpack-off log input=<mint+run>.txt
```

Emulated frames are identical across arms: Castlevania 3 607, Zelda 5 109.
Repeated runs are deterministic (`hires.txt` byte-identical between passes of
the same arm). Coverage counts distinct `(tileData, palette)` keys on the
`<tile>` lines of the emitted `auto/textures/hires.txt`, condition prefixes
ignored, against the keys named by any sheet sidecar (`sheets/*.json` with a
sheet PNG). A mirrored sprite cell is credited with its `source` key: the
unflipped key the run time looks up (ADR-0178), which is also the key
`mep_build` emits for it.

## Does the baseline reproduce ADR-0209?

- **Castlevania: exactly.** 3 209 keys, 2 673 distinct shapes, 514 shapes
  reachable when the sidecar's `tile` field is matched as written, so
  19.2 %.
- **Zelda: closely, not exactly.** 2 153 keys (ADR-0209: 2 171), 1 620 shapes
  (1 615), registry 294 (277), 260 reachable shapes, which gives 16.0 %
  against 17.2 %. ADR-0209's 17.2 % is registry size over hires shapes
  (277/1615). The same ratio here is 294/1620 = 18.1 %. The drift is
  attributed to recorder changes since 2026-09-19. That is not proven, and
  ADR-0209 does not record exactly how its Zelda input was driven.
- **ADR-0209's figure also mixes two things.** Matching the sidecar's `tile`
  field as written misses mirrored sprites, whose sheet art is flipped
  (ADR-0178). Crediting `source` puts Castlevania's baseline at 532 shapes,
  or 19.9 %. The ADR-0209 numerator is "registry" on one game and
  "reachable" on the other (Castlevania registry is 592, not 514).

### Reading the costs

- **Registry**: +19 (Castlevania), +0 (Zelda). That is under 1 % of the
  `uint16_t` id space (`kEmptyCell` = 0xFFFF). Past the cap `ShapeIdFor`
  returns `kEmptyCell` and the tile is dropped from the sheets rather than
  corrupting them. Under (i) the registry is bounded by the distinct drawn
  shapes (plus mirrored forms), so a CHR RAM game would need about 65 000
  distinct drawn tiles to reach it. Nothing measured here comes close.
- **Grid dump**: `K` lines are written only for shapes that appear in a
  retained frame, so the count is unchanged (342 / 190). The file shrinks
  about 0.1–0.4 % because ids are renumbered.
- **`sheets/`**: +5.6 KB on Castlevania (the 19 `unsorted` cells), −1.4 KB on
  Zelda (re-coloured cells). File counts are unchanged.
- **Wall clock**: no difference could be told apart from noise. A parallel
  28-ROM re-score sweep was running `headless_record` on the same machine, and
  the spread *within* one arm (up to 15 s on the first pass) dwarfs any gap
  *between* arms. The per-tile interning cost cannot be resolved at this
  precision. A cost of about 5 % is not ruled out.
- **Line ceiling**: the one-line hook fits `HdPackBuilder.cpp`'s ADR-0137
  ceiling with 0 lines to spare. Any real implementation larger than that
  needs a ceiling amendment, as ADR-0229 says.

### A side effect the prototype has: the organised output moves

ADR-0229 expects (i) to leave the organised sheets unchanged. The prototype
does not. `ShapeIdFor` makes "the first exact variant seen" the shape's
drawable art and assigns ids in first-sight order. Once `ProcessTile` interns
first, both the ids and the first-seen variant change:

- **Castlevania**: the key sets of every organised sheet are unchanged, but
  `misc`, `spr000` and `sprites` PNGs differ (cell order). In `hires.txt`,
  76 `spriteNearby` conditions changed their anchor tile. The unconditioned
  `<tile>` set is identical.
- **Zelda**: 20 sheet PNGs differ. `metatiles`, `object` and `sprite(s)` each
  lose 1–2 keys and gain 1–3, because a cell now shows another palette of
  the same shape. `spriteNearby` conditions whose palette is not a sprite
  palette, so they can never fire, go from **1 to 6**. One example: tile
  `000000FF00FFFF00…` was anchored with `FF303B22` and is now anchored with
  the background palette `36303B22`.

A variant of (i) that avoids this is to intern the drawn-but-unregistered
shapes **at save time** instead of on the PPU path, after the retained streams
have fixed every existing id and art. That variant was not measured. By the
coverage numbers above it would reach the same keys, which is none that were
not already reachable.

## Round trip (ADR-0183 §4)

The procedure copies the recorded pack, promotes `auto/textures` to
`textures`, runs `python3 scripts/mep_build.py build <copy> --quiet`, and
then runs the same build a second time. All four runs report 0 errors. The
second build's `textures/hires.txt` is byte-identical to the first. No key
is added. The carried set equals the sheet-reachable set measured above (532
/ 532 / 262 / 263). `mep_build` itself reports the drop:
`3209 in the key source -> 532 carried, 2677 dropped`, and calls it expected
under ADR-0172. That is an independent check on the coverage figure: the
rebuilt pack holds exactly the keys the sheets reach, and option (i) does not
change the Castlevania set.

## Caveats

- Two recordings, both CHR RAM games. On a CHR ROM game, `defaultTile`
  entries come from `AddRomTiles` instead of the PRG scan. The split between
  "drawn" and "static" should look the same, but that was not measured.
- Zelda's baseline drifts from ADR-0209's by 1–2 points (above). The
  before/after comparison is unaffected because both arms come from one
  binary.
- The wall clock was measured on a shared machine. See "Reading the costs".
- The prototype is a measurement aid, not the F14.4 implementation. It has no
  unit test of its own.

## Out-of-scope findings (not fixed here; filed as #415 and #416)

1. **A `spriteNearby` condition can name a background palette** (#415; on `main`,
   Zelda "before" arm): `spr018_n0,spriteNearby,0,8,0000…0000,09010001,Y`.
   To reproduce, record Zelda as above and look for `spriteNearby` lines in
   `hires.txt` whose palette does not start with `FF`. Expected: a sprite
   palette, or no condition. Observed: the palette the shape was first drawn
   with as background, so the condition can never be true. It looks like the
   same "first-seen variant is the art" mechanism described above. The
   prototype makes it 6.
2. **Map placements that do not resolve** (#416; on `main`, Castlevania): `mep_build`
   warns `map-000.png: 3 placement(s) do not resolve in the metatile
   vocabulary — skipped`. Expected: every map placement names a cell of the
   sibling `metatiles.json`. Observed: 3 do not, and those crops are lost on
   rebuild.
