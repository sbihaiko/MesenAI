## Method

1. **"After" packs** (source of the tag-on pack): F12.16's already-recorded
   30-ROM library, `.../32f3f03a-.../scratchpad/f1216lib/lib-after/<rom>/`
   — each carries `<bgPreservesBehindBgSprites>` (the F12.15 recorder writes
   it unconditionally). Confirmed present for all 30 ROMs before use.
2. **`tag` / `notag` install directories**
   (`scratchpad/adr0224-sweep/prep_packs.sh`): for each ROM, copied the
   after-pack's `auto/` subtree twice, into `<rom>.nes` + `<rom>/auto/...`
   layout (the sibling convention `headless_record` needs). `notag` had the
   one `<bgPreservesBehindBgSprites>` line deleted with `grep -v`; `tag` is
   untouched. Verified per ROM: tag pack has exactly 1 tag line, notag has 0.
3. **Grid dumps** (`gridgen.sh`): one fresh 60 s bootstrap recording per ROM
   (`MESEN_SHEET_GRID_DUMP=<d>/grid.txt <rec> <d>/rom.nes 60 <d>/run bootstrap
   log`), ROM copied to a scratch dir so no sibling pack is discovered — same
   route as F12.13/F12.15/F12.16. All 30 finished `rc=0`, ~20–23 s wall clock
   each (NES emulation runs well under real time headless). This is the
   classification input for `measure_capture_overdraw.py --grid`; it is a
   separate recording from the sweep's screenshot renders, matched to them by
   background-plane content (deterministic power-on route, no input), the
   same method F12.13/F12.15/F12.16 use.
4. **Render sweep** (`render_sweep.py`): for each ROM, 4 timestamps (10 s,
   25 s, 40 s, 55 s from power-on) x 3 configurations — `none` (`hdpack-off`
   baseline), `tag`, `notag` — each its own working directory (the harness
   trap: `headless_record` places `mesen-home/Screenshots/` next to the
   *parent* of the output prefix, so distinct timestamp/config renders must
   not share a parent directory). 360 runs total, all `rc=0`, every one
   logging a `capture finished: N frames (target M), Xs of wall clock` line
   used for the cost table. No run needed more than 11 s of wall clock (the
   55 s timestamp cases); nothing near the 5-minute budget.
5. **Classification** (`aggregate.py`, wrapping
   `scripts/measure_capture_overdraw.py`): for each ROM, ran the tool twice
   at `--sprite-height 8` and twice at `16` (tag and notag against the
   shared `none` baseline, `--verdict background`), and kept whichever height
   gave fewer `erased_sprite_unattributed_cells` summed over both
   configurations (ties keep 8). 29 of 30 ROMs resolved to height 8; **Bubble
   Bobble** resolved to 16 (its sprites are 8x16 on this route). One
   methodology bug found and fixed while aggregating: the tool's exit code is
   the ADR-0224 §4 verdict (1 when `erased background > 0`), not a run
   failure — the first aggregation pass wrongly treated Tetris's exit 1 (6
   erased-background cells, present in both configurations, unrelated to the
   tag) as a tool crash. Fixed by checking the JSON output file landed,
   not the return code; re-run picked it up correctly and no ROM was
   ultimately skipped.
6. **Byte-identical count**: `filecmp.cmp(shallow=False)` between the `tag`
   and `notag` PNG at each of the 4 timestamps, 120 pairs total.
7. **Cost**: sum of `capture finished` wall-clock seconds and frame counts
   for the `tag` and `notag` configurations (excluding the `none` baseline),
   per ROM and totaled, converted to ms/frame.

## Conclusion

- **`erased background` is byte-for-byte identical between `tag` and
  `notag` on every one of the 30 ROMs** (6 = 6 on Tetris, 0 = 0 on the other
  29) — exactly what ADR-0224 §2 predicts: the tag only re-applies the
  behind-background sprite pass after layer 2 on colour-0 background pixels;
  it never touches the background plane itself. Tetris's 6 cells are present
  identically with the tag on and off, so they are the pre-existing card-type
  loss ADR-0223 already accounts for, not something this tag causes or
  fixes.
- **The tag never *increases* erased cells anywhere in the library.**
  `erased sprite` either stays equal (26 of 30 ROMs, both 0) or drops with
  the tag on (Bubble Bobble 255 -> 1, Ice Climber 6 -> 0, Metroid 106 -> 0,
  Pac-Man 2 -> 0); it is never higher with the tag than without. Summed:
  **369 -> 1** erased-sprite cells across the library, of which **200 -> 1**
  were behind-background sprites — the exact mechanism ADR-0224 targets. The
  4 ROMs affected are exactly the ones with a behind-background sprite drawn
  over a colour-0 background cell on this route; the other 26 render
  byte-identically or near-identically regardless.
- **Byte-identical frames: 110 of 120** (30 ROMs x 4 timestamps) between
  `tag` and `notag`; all 10 non-identical pairs are in the four ROMs above.
  Note a non-identical pair does not always carry an `erased` cell (e.g.
  Metroid is 1/4 byte-identical but 0 erased-sprite with the tag at every
  point) — consistent with F12.15's finding that some pixel differences are
  the upscale filter drawing sprite edges differently, not a correctness
  difference the cell metric would flag.
- **Render cost: no measurable difference.** Library-wide, **3.711 ms/frame
  with the tag vs 3.741 ms/frame without** (-0.8%), on 234 480 frames per
  configuration — inside run-to-run noise (per-ROM deltas range from tag
  being ~17% faster, e.g. Dr. Mario, to ~4% slower, e.g. Donkey Kong, with no
  consistent direction). ADR-0224's predicted extra branch (one per pixel
  per layer-2 background, only on packs with the tag and only on pixels with
  a behind-background sprite) does not show up above the noise floor of a
  shared machine running other jobs concurrently during this sweep (see
  caveat below) — matching F12.15's Punch-Out!!-only finding (-0.3%) at 30x
  the ROM count.
- **Answer to ADR-0224's render-cost clause:** measured, not assumed, across
  the full 30-ROM library — the tag costs nothing measurable and never
  increases the erased-cell count in either column.

## Anomalies / caveats

- **Shared machine.** Other `headless_record` and build jobs from a
  different, concurrently-running Claude session (a separate worktree,
  `agent-a410879e1f06066c8`) were observed running on the same machine during
  parts of this sweep (`/bin/ps`). The wall-clock ms/frame numbers above are
  therefore not a clean-room benchmark, same caveat F12.15 already recorded
  for its own cost table.
- **Tetris's 6 `erased background` cells** are identical with the tag on and
  off — not a regression this tag introduces, and not something it fixes;
  flagged here only because it is the sole nonzero `background` entry in the
  table.
- **Grid dump vs sweep render are separate recordings of the same
  deterministic route** (no input, bootstrap, power-on), matched by
  background-plane content rather than being the literal recording the
  sweep replays — same method F12.13/F12.15/F12.16 use, not a new
  assumption introduced here.
- **Sprite height** was decided by re-running the classifier at both heights
  on already-rendered frames (cheap — no re-recording) and picking the one
  with fewer `unattributed` erased-sprite cells; Bubble Bobble is the only
  ROM in the library where 16 wins over 8.
- **A methodology bug was caught and fixed during this run** (see "Method"
  step 5): treating the classifier's exit code as a failure signal instead
  of the ADR-0224 §4 verdict it actually is. No other tool or script defect
  was found.

## No out-of-scope bugs found

Nothing observed here rises to a reportable bug: all 360 renders succeeded,
every pack loaded with `tiles > 0`, and the one anomaly (Tetris's 6 identical
`erased background` cells) is the already-tracked ADR-0223 card cause, not a
new defect.
