Three things carry the result:

1. **Metroid's Norfair background does not animate on the NES.** Across
   the 2023 frames of the route spent in Norfair (RAM `$74` = `$11`; two
   doors, the lava corridor with its jumpers and flyers), no background pattern slot changed
   and no background palette byte changed; the nametable changed only at
   doors and camera moves, and the cycle search found nothing on any of the
   1179 background tracks. The reference pack's `NorfairFrame1..8`
   (`frameRange,96,…`) and `NorfairLavaFrame1..5` (`frameRange,64,…`) are
   therefore **animations the author added over static tiles**. There is no
   game phase for them to match, so they are correct by construction against
   any counter — they are not evidence that a recorded cycle could be dated.
2. **Every Metroid sprite cycle is input- or spawn-locked**: 3 keep one
   phase inside a recording but land on another phase in the shifted
   recording, 3 do not keep one phase even inside a recording. All six have
   6- or 9-frame turns; a period of 6 or 9 does not divide 256, so it cannot
   be the game's 8-bit frame counter taken mod a period, and it is not.
3. **Contra's water shimmer (palette bytes 9, 14 and 15, 4 phases x 8
   frames) is counter-locked between two recordings whose stage load differs
   by 92 frames — and stops being so after a game over.** Its 8-frame step
   follows the game counter `$1A`; which phase comes next restarts at every
   stage load. A third recording that continues after a game over puts the
   same cycle 2 frames (of 32) away from its pre-reload phase against the
   PPU frame counter, because `$1A` stalls for 6 frames on the game-over
   screen and 8 on each stage load while the PPU counter does not.

## Definition

`frameRange` is `FrameNumber % A >= B` (`HdPackConditions.h`), and
`FrameNumber` is the PPU's `_frameCount` (`HdNesPpu.cpp`): counted from
power-on, never paused, carried in a save state (`NesPpu.cpp` serializes it).
A cycle is **counter-locked** when its phase is a function of that number
alone:

- The cycle's **turn length T** is the most common gap, in frames, between
  consecutive entries into its anchor phase.
- Its **anchor** is phase 0 of the content-canonical rotation: the rotation
  whose sequence of content keys (sha1 of the tile or pose bytes, or the
  palette value) is smallest. The Core's own rotation puts the most-seen pose
  first, which can differ between two recordings; a content key cannot.
- For every entry into the anchor phase inside a cycle window, take the
  global frame number mod T. The window's first run is excluded: it is
  entered from outside the loop (a track appearing, a screen loading), so its
  start is not a phase boundary.
- Verdict per cycle, over recording A and recording B of the same route:
  **counter-locked** if every residue in A and B is one value;
  **drifts within a recording** if A or B alone holds more than one;
  **shifted between recordings** if each holds one and they differ;
  **unpaired** if the cycle is in only one recording. Zero-frame tolerance.

Sprite cycles are keyed by content only, as `PoseStats.Cycles` is (one cycle
entry merges every track that shows the loop); a frameRange on those poses
would have to serve all of them. Background tracks have a stable identity in
two recordings of one route, so the pattern slot, palette byte or nametable
address is part of their key.

### Why a shifted start separates the two hypotheses

Both recordings start at power-on with RAM zeroed and play the same inputs;
B inserts idle frames before the route. An animation driven by a counter
that runs from power-on keeps its phase against the PPU frame number no
matter when the route happens. An animation timed from something the route
does (a spawn, a button, a screen load) moves by the inserted frames mod T.
The shift has to be coprime with the periods found (37 for Metroid; the
Contra shift ends up as 92), and it has to actually move the route — which
the first Contra attempt showed is not a given (below).

## Method

### The probe

`headless_record` records the retained OAM stream, which drops frames with
no sprite and never says which global frame a retained frame was. A
scratchpad harness (`cycle_probe.cpp`, not in the repo) linked the same
dylib, set up the run as `headless_record` does (NES pad on port 1,
`RamState::AllZeros`, HD packs off, no frame limiter), loaded the same kind
of input script, and stepped the run **one emulated frame at a time**
(`HeadlessSetPauseFrame(f)` + `Resume`), reading at every pause, through
`HeadlessCaptureNesSpriteLayer` and `HeadlessReadNesRam`: the PPU state
(`FrameCount`, pattern-table selects, loopy `t`, fine X), OAM, palette RAM,
`$0000-$1FFF` pattern tables, `$2000-$2FFF` nametables and the 2 KB RAM.
`FrameCount` advanced by exactly 1 between consecutive records in all
five recordings.

### The analysis

A scratchpad script re-implemented the path `SpriteGrouping::BuildPoses`
takes to `PoseStats.Cycles` — `SegmentFrame` (DSU within `kPoseMaxGap` = 8
on both axes, clusters of `kPoseMinTiles` = 4, `(node, dx, dy)` sets rounded
to cells), poses kept at `kPoseMinFrames` = 3, `LinkPoseTracks`
(nearest-first within `kPoseTrackMaxMove` = 16, ADR-0226's one-frame
bridge), and `FindPoseRuns`' cycle half (period 2–16, at least 2 repeats and
2 distinct poses) — on the per-frame OAM, so each run carries its global
frame. Background tracks go through the same period search: each of the 256
slots of the background pattern table (16 bytes), each of the 13 background
palette bytes, and each nametable tile byte across stretches where the
camera (`t`, fine X) holds still for at least 32 frames.

**The re-implementation reproduces the recorder.** `headless_record … 56
bootstrap hdpack-off` on Metroid route A wrote a `poses.json` with 6 cycles:
periods 2, 2, 2, 3, 2, 2 and repeats 49, 31, 17, 13, 7, 6. The script finds
the same 6 on the probe's recording of the same route, with the same periods
and the same repeat counts. Their ids below are the recorder's.

**The probe is deterministic.** Metroid route A recorded twice is
byte-identical over all 3364 frames (47 MB each). There is no run-to-run
noise for the verdicts to absorb.

### The routes

- **Metroid** has no route to Norfair in the repo. `JUSTIN BAILEY ------
  ------`, typed on the password grid after CONTINUE, starts Samus in
  Norfair (RAM `$74` = `$11` from the first gameplay frame). Route after the
  password: `200f -`, then runs right with shots and a jump (`6f B`, `120f
  R`, `200f R` x2, `100f RA`, `200f R`), then back left (`200f L`, `300f L`,
  `100f LA`, `300f L`) — 3364 frames in all, 2023 of them in Norfair.
  B = the same script behind **37** idle frames at power-on. The route held:
  at A[i] vs B[i+37] the nametables and scroll are identical in 3350 of 3364
  frames, and the game counter `$2D` holds the same offset to the PPU counter
  in 3350 of 3364 (all 2064 after the password).
- **Contra**: the Konami-code mint (`mint-stage1-30lives.txt`), `60f L`,
  then `stage1-water.txt` — Bill drops into the water at the start and
  shoots from there, so the camera never moves and the water stays on screen
  (4671 frames). **A 37-frame lead did not move the route:** the stage loads
  at frame 596 in both, and B was identical to A in 4651 of 4671 frames — the
  title holds the stage start until its own timer, whatever frame Start came
  on. A 200-frame lead moves the stage load to 688 (+92), so B is the
  200-frame lead with the post-Start idle cut from 550 to 442 frames, so that
  every in-stage input lands exactly +92 as well (4763 frames). At A[i] vs
  B[i+92], `$1A` holds the same offset to the PPU counter in all 3971 frames
  from the stage on.
- **Contra C** (the third recording, within-session check):
  `mint-stage1.txt` (3 lives), `550f -`, `50f -`, then `240f R`, `30f RB`,
  `240f R`, `40f RA`, `20f R`, `240f R` — Bill runs into the enemies and the
  game is over at about frame 2476 — `1000f -`, `1f T` on CONTINUE at frame
  3311, stage reload (`$1A` stalls 3508–3515), then idle in the reloaded
  stage to 5112 frames.

Total probe wall clock was about 2–3 minutes per recording (36 ms per
stepped frame); every run's frame budget was fixed by its script.

## What the numbers imply — not a decision

- On these two inputs, the one place a recorded cycle is counter-locked is a
  background palette animation, and it holds only until the first reload.
  The Metroid case the evidence doc pointed at — `NorfairFrame1..8` as the
  "animation locked to that counter" — is not a recorded cycle at all: the
  NES draws those tiles static, so a phase can be chosen freely, which is
  what the author did. A generated `frameRange` for an **authored**
  animation needs no observed phase; one for a **recorded** cycle needs a
  phase that, here, survives neither a spawn (sprites, 0/6) nor a game over
  (Contra water).
- ADR-0189 §4's split ("correct only for an animation locked to that
  counter, and silently wrong for anything the player triggers") holds on
  every recorded cycle measured, with one refinement: even the
  counter-driven animation is locked to the *game's* counter, which stalls
  on loads, not to the emulator's, which does not.
- The amendment the PRD row anticipates therefore has two separable
  questions: frameRange for animations an artist adds over static art (no
  phase to observe), and frameRange from `PoseStats.Cycles` or a background
  cycle (a phase that, on these numbers, does not stay put).

## Limits

- Two games, one route each, as the slice bounded it. The Contra sprite axis
  is empty on this route, and Metroid's background axis is empty on the NES.
- Within-recording drift for sprite cycles mixes two causes the verdict does
  not separate: several objects on one loop at different phases, and one
  object whose loop pauses (a stretched turn).
- The scripts were scratchpad-only (a stepping probe linked against the
  dylib, and the analysis described above); nothing under `scripts/` was
  added or changed.
- No bug was found. The 37-frame Contra lead not moving the stage start is
  the game's title logic, not an emulator defect.
