# F12.1 — scale and load measurement (2026-09-17)

Scope and stop rule live in the PRD (Part A §4, Phase 12, row F12.1): time
`NesConsole::LoadHdPack` on the installed Metroid pack and on a synthetic
300 000-line `hires.txt`; emulation throughput (emulated frames per wall
second, with and without the pack) and peak memory over a 60 s headless run;
`mep_build.py build` and `mep_lint.py` wall time on a 300 000-line project.
Numbers only — no optimization landed in this slice.

This log is what F12.3's reload strategy and any later optimization cite.

**The three PRD numbers, each with the definition it came from.** All three
reproduce once the third one's definition is named, which is what this
paragraph is here to do.

- `67` images — distinct `<img src>` targets, and `ImageFileData.size()`.
- `150 199` tile rules — `HdPackData::Tiles.size()`, the loader's rule count,
  not the 150 250 raw `<tile>` occurrences.
- `8401` keys — distinct `(tileData, palette)` pairs over the pack's `<tile>`
  rules: the count `scripts/artist_cover.py` prints and the one
  `docs/validation/metroid-artist-workflow-evidence.md` records. Re-counted

The first version of this log called 8 401 unreproducible and left the PRD
number alone. It had measured **9 197** instead — `TileByKey.size()` — which is

`PaletteColors` + the 16 `TileData` bytes **plus `TileIndex` and
`IsChrRamTile`**, so one `(tileData, palette)` pair can occupy more than one
entry. Two numbers, two definitions, neither wrong. Corrected when F12.1's row
was consolidated into PRD §3; how the 9 197 entries split across those two
extra fields was not derived here.

## 1. `NesConsole::LoadHdPack` and the bitmap decode

`seconds=60` (3 607 emulated frames), 3 clean reps per configuration. The
number is the `[MEP] LoadHdPack:` line the Core itself emits.

| Configuration | `LoadHdPack` (ms, 3 reps) | median | `LoadAsync` (ms) | images |
|---|---|---|---|---|
| Metroid, sibling `mep/textures` (what this ROM loads) | 412 / 774 / 405 | **412** | 13 671 / 13 167 / 14 970 | 271 |
| Metroid, loose `HdPacks/Metroid (USA)` (legacy control) | 431 / 403 / 436 | **431** | 15 252 / 15 919 / 16 444 | 271 |
| Synthetic, exactly 300 000 lines | 326 / 295 / 270 | **295** | 1 145 / 1 298 / 1 160 | 67 |
| No pack (`hdpack-off`) | — (the function returns before the timer) | — | — | — |

Six reps were taken per line (this pass plus an earlier identical pass, same
binary); the medians over all six are 409 ms (sibling, range 397–774), 434 ms
(loose, range 397–457) and 281 ms (synthetic, range 231–326).

**`LoadHdPack` is not the load.** It parses the manifest and returns; the
bitmaps are decoded by `HdPackData::LoadAsync` on a detached thread, and that
decode is **30–40× the parse** — 13–16 s against 0.4 s for the same pack. It
is the number a reader waiting for a pack to appear actually pays, and F12.3
cannot inherit a reload strategy from the 0.4 s figure alone.

Synthetic vs real is not a clean per-line ratio: the synthetic manifest has no
`<background>` lines and no condition errors, and the real one writes 8 234
`[HDPack]` error lines through `MessageManager::Log` during the same window.

## 2. Throughput and peak memory, 60 s headless run

`seconds=60`, frame limiter off (`EmulationSpeed 0`), 3 reps. Frames per wall
second is `capture finished` frames ÷ that line's own wall clock; peak RSS is
`/usr/bin/time -l`'s `maximum resident set size` for the whole process.

| Configuration | fps (3 reps) | median | peak RSS (MB, 3 reps) | max |
|---|---|---|---|---|
| Metroid, sibling | 259.5 / 255.8 / 228.3 | 255.8 | 2988.5 / 2533.6 / 2179.7 | **2988.5** |
| Metroid, loose | 218.6 / 204.9 / 200.4 | 204.9 | 2718.9 / 2759.4 / 2724.4 | **2759.4** |
| Synthetic 300 000 lines | 346.8 / 334.0 / 334.0 | 334.0 | 469.1 / 469.5 / 469.1 | **469.5** |
| No pack | 474.6 / 508.0 / 508.0 | 508.0 | 24.1 / 23.8 / 24.3 | **24.3** |

These 60 emulated seconds run with the bitmap decode still going, so the
figures are "the first minute the user sees", not a steady state. §4 repeats
the four configurations ten times longer to check whether that distinction
survives measurement — it does not; both spans agree within drift.

Memory tracks the pack's images and audio, not its rule table: 300 000 rules
with the same 67 images cost 469 MB, the full 277-image pack costs 2.2–3.0 GB,
and the emulator without a pack costs 24 MB.

## 3. `mep_build.py build` and `mep_lint.py` on a 300 000-line project

3 reps each, `/usr/bin/time -l`.

| Tool | wall (s, 3 reps) | median | peak RSS (MB) |
|---|---|---|---|
| `mep_build.py build` | 2.72 / 2.70 / 2.70 | **2.70** | 857.1 |
| `mep_lint.py` | 0.59 / 0.59 / 0.65 | **0.59** | 165.3 |

`build` reports `300000 tile(s), 1 sheet(s), scale 1` and `300000 carried, 0
dropped`; its own embedded lint reports `0 error(s), 0 warning(s)`. `lint` on
the built tree reports `ver 108, scale 1, 1 images, 300000 tiles, 0
conditions`, `0 error(s), 0 warning(s)`.

**Linting an *un*built project is 0.80 s and 300 000 errors**: the source
`hires.txt` has no `<img>` line, so every `<tile>` references a nonexistent
image. The 0.59 s figure is the valid-project one and is the one to quote.

## 4. Companion run, 600 emulated seconds

The 60 s run sits entirely inside the bitmap decode window, so the same four
configurations were run for 600 emulated seconds (2 reps, same binary) to ask
whether the throughput rises once the decode is out of the way.

| Configuration | fps (600 s) | median | `LoadAsync` (ms) | peak RSS (MB) |
|---|---|---|---|---|
| Metroid, sibling | 188.2 / 206.6 | 197.4 | 15 798 / 17 912 | 2848.3 |
| Metroid, loose | 230.3 / 248.3 | 239.3 | 18 532 / 14 797 | 2893.9 |
| Synthetic 300 000 lines | 353.5 / 353.2 | 353.4 | 1 061 / 1 172 | 485.0 |
| No pack | 555.6 / 559.1 | 557.4 | — | 40.7 |

**No separate steady state emerges.** Against the 60 s medians in §2 the
600 s ones move both ways and by less than the run-to-run spread of each:
sibling 255.8 → 197.4 (−23 %), loose 204.9 → 239.3 (+17 %), synthetic 334.0 →
353.4 (+6 %), no pack 508.0 → 557.4 (+10 %). The two byte-identical pack
copies move in opposite directions, which is drift, not an effect of the
decode window. Read together with §2: the one-off decode costs a few per cent
of the run, not a factor, and the sustained cost of this pack is the HD render
path itself.

The `LoadAsync` wall figures do not shrink with a longer run either. On an
8-core host with two saturating threads the decode's wall time is largely a
measure of how much CPU the emulation thread leaves it, which is why it reads
14.8–18.5 s here and 13.2–16.4 s in §2 for the same 271 images.

## Findings

1. **The pack's *load* is the decode, not the manifest.** 13–16 s of detached
   bitmap decoding against 0.4 s of parsing, for 271 images / 23.9 MB of PNG.
   Any F12.3 reload design that only re-reads `hires.txt` would be fast and
   wrong; per-image invalidation is the shape this number points at. (The
   pack's *running* cost is a third thing again — see finding 3.)
2. **This pack is partially broken and loads anyway.** 8 234 `[HDPack]`
   errors: 8 222 are `Condition not found:` across 27 condition names never
   defined with a valid `<condition>` line (`!SamusInTheAir` alone 2 400×,
   `Samusframe1`–`9` 480× each), and 12 are
   `Error while loading background: LavaAirGlow0.png` — the only missing one
   of 205 distinct `<background>` targets, which is exactly why
   `BackgroundFileData` ends at 204. The run still renders at a 100 % bg tile
   match rate. Errors here are noise, not failure, and the 8 234 log lines are
   inside the measured load window.
3. **Throughput.** Without a pack the M1 Air does 475–564 fps at 60 s
   (median 508) and 555.6–559.1 at 600 s (median 557). With the Metroid pack
   it does 200–260 fps at 60 s (medians 256 sibling / 205 loose) and
   188–248 at 600 s (medians 197 / 239). The pack costs between a third and a
   half of the frame rate and keeps costing it — the one-off decode is not the
   reason. The spread inside one configuration is larger than the gap between
   the two byte-identical pack copies, so the copies are not distinguishable
   by throughput.
4. **Memory.** Peak RSS with the pack is 2.2–3.0 GB at 60 s (2.35–2.89 GB at
   600 s) against 24 MB (40.7 MB at 600 s) without it, and 469 MB for a
   300 000-rule synthetic that shares the real pack's 67 images. The rule
   table is not the memory story; the images and the 212.8 MB of OGG are.
5. **The toolchain is not the bottleneck at this scale.** 300 000 lines cost
   `build` 2.70 s and `lint` 0.59 s. Nothing in F12.3–F12.7 needs to be
   defended against the Python side at this size.

## Reproduction

```
make capture-tool        # CLT make + CLT clang++, -O3, per CLAUDE.md
caffeinate -dimsu scripts/headless_record <rom> 60 <dir>/out log
```
The scratch home is `<dir>/mesen-home`, created by the tool; the loose-pack
runs put a `HdPacks/<rom name>` symlink to the pack inside it. The emitted
`<home>/mesen.log` holds every `[MEP]` line (the 1 000-entry in-memory log is
not enough for this pack). `mep_build.py build <project>` then
`mep_lint.py <project>`; nothing else is needed.

The synthetic manifest is generated, not shipped: `<ver>108`, `<scale>2`, the
pack's own 67 `<img>` lines, eight `<condition>Name,memoryCheckConstant,…`
definitions, then `<tile>` lines in the loader's `ver>=100` form —
`<tile>bitmapIndex,tileData,palette,x,y,brightness,defaultTile` — with
`bitmapIndex=0`, a 3-hex-digit CHR index, an 8-hex-digit palette, and a
condition prefix on 40 % of them, up to exactly 300 000 lines. The MEP project
is one legacy 16-column sheet at `scale 1` (8 px cells, 128×150 000 px =
300 000 cells) plus a 300 000-`<tile>` source `textures/hires.txt`, so `build`
reads 300 000 keys and writes 300 000 rules back.

## Honest limits

- **Not measured: a warm, steady-state reload.** No reload path exists yet;
  F12.3 owns it.
- **`LoadAsync`'s 13–16 s is wall time under contention**, not CPU time: it
  runs on a detached thread beside an emulation thread that is itself
  saturating a core, on an 8-core machine. `HdPackBitmapInfo::Init` is
  `_initDone`-guarded, so the two threads never decode the same image twice,
  but the split between them is not instrumented.
- **Thermal drift is real and visible.** The same no-pack configuration
  measured 554.9–563.6 fps early in the session and 474.6–508.0 fps later,
  10–16 % lower; the same happened to the two pack configurations. The fanless
  M1 Air throttles under a sustained load, so a 60 s burst and a 600 s run are
  not directly comparable, and short bursts are not comparable across the
  session. The clean pass is the one logged; §4's run also shared the host
  with a `make doc-checks` invocation for part of its wall clock.
- **One host, one pack, one ROM.** No second machine, no second community
  pack, no GB/SMS pack, no CHR-RAM pack. The synthetic is a manifest, not an
  art set.
- **Not measured: the GUI's own load path.** Every number here is headless.
  Whether the client's post-`GameLoaded` background identity refresh (the
  P.1-local cache slice, not yet on this branch's base) or the video-filter
  pipeline adds to the decode window is out of this slice.
- **Not measured: `mep_lint.py` on a 300 000-line *zip*.** Both tools were
  measured on an extracted project folder. The CI path lints the artifact, and
  reading it through `Source.from_zip_bytes` is a different code path from
  reading `textures/hires.txt` off disk.
- **`mep_build.py build` was measured once the project was already built**, so
  its key source in reps 2 and 3 was the 300 000-line output of rep 1. The two
  are the same length and the same keys (`300000 carried, 0 dropped`), so the
  number is not affected; saying so is cheaper than a second project.
