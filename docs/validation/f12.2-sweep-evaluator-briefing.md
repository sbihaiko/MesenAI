# F12.2 — evaluator briefing, one game, no answer key

This is the **only** document an evaluator of F12.2 is given besides the three
artist guides, the per-game index, and the sandbox folder below. It is not the
dispatcher script. If you have also been handed
`f12.2-copy-sheet-cell-panel-script.md`, ADR-0214, the PRD, or any
`scripts/*.py` source, **stop and say so** — the run is invalid.

You are evaluating **one** game. The dispatcher names it. Your inputs are
listed, with absolute paths, in `index/<game>.md` — read that first. Fill a log
at `out/log-<game>.md`, in the shape the Zelda C.5 log uses: Binary and
inputs, the verbatim step log with clock times, the results table below, then
Defects. Start the clock at the first launch and stop it when the repainted
shape is on screen, or when you give up.

## Who you are

You are a NES pixel artist. You have shipped two HD packs by hand-editing
`hires.txt` with a spreadsheet beside you, and you are trying this emulator
for the first time. You may read the three guides in `guides/`. You may
**not** open any `textures/hires.txt` at any point — that is a fail, logged
with the clock time and the question it answered. There is no post-build
exception: the copy the build just rewrote is the same file, and the build
prints the rule you would have been looking for (step 4 of the goal). You
may **not** read `tools/` or `bin/` source; run those programs, never read
them.

## Contamination you did not go looking for

Two things reach you automatically, before you have read a single sandbox
file, and neither is something you can decline: a `gitStatus` system-reminder
naming this checkout's branch and recent commits, and (if this account has
run this task before) your own persistent memory. Both have, in past runs of
this exact protocol, named the feature under test verbatim in a commit
subject or a memory bullet — that is a leak of the answer to criterion 1, not
a hint you are meant to use.

Rules for both:

- **Never run** `git log`, `git show`, `git blame`, `git diff`, or any other
  history command, and never open `.git/` — that would only compound a leak
  you cannot undo, and it tells you nothing the sandbox doesn't already give
  you honestly.
- **Never act on persistent memory.** If you already "know" something about
  this repository, this feature, or a prior F12.x run from before this
  message — a memory file, a prior session, anything not written in the
  sandbox or this briefing — treat it as inadmissible. Do not use it to find
  the tile, to write the log, or to skip a step "because you already know it
  works."
- **Log it, don't launder it.** If the gitStatus reminder or your own memory
  already names or implies the action under test before you have found it
  yourself from `tilemap-menu-labels.txt`, write that down verbatim as a
  **Contamination** line in your log the moment you notice it — quote the
  exact commit subject or memory line. This voids criterion 1 for your run;
  it does not void the rest of the protocol. Keep going through steps 2-5 as
  if you had found the action honestly, and say so in your five-line summary.
- Silence here is worse than a caught leak: an evaluator who noticed the leak
  and used it anyway, without saying so, produces a false pass that looks
  identical to a real one.

## Goal

Within twenty minutes, from that game's paused frame:

1. Pick one background shape you can see on that frame and want to
   recoulour (a bush, a rock, a ground or wall tile — not a sprite).
2. Get that tile's identity out of the running emulator in a form you can
   paste into a sheet sidecar, **without typing hex from a spreadsheet** —
   by naming the menu entry you would click, and reading that tile's line
   out of `tilemap-copy/<game>.txt`.
3. Paste it as a new cell on whichever sheet of your work copy's
   `textures/sheets/` you judge the copied key belongs to. The copy names a
   tile, not a sheet, and this pack may have several; the guide's *What a
   cell is* is where that judgement is written down. Grow the sheet's `.png`
   / `.orig.png` only if it has no free slot; paint a 32×32 solid magenta
   square at the new cell's top-left; leave `*.orig.png` unpainted except
   for a resize.
4. `python3 tools/mep_build.py build <your work copy>` must exit 0 with no
   `error:` lines, and it prints a `report:` row for every cell you painted
   or pasted, naming the `<tile>` rule that cell produced, its crop and its
   sheet. **That row is where you read the round trip** — there is nothing
   to look up in the rebuilt `textures/hires.txt`, and opening it is still a
   fail of criterion 4. `python3 tools/mep_lint.py <your work copy>` must
   exit 0.
5. Copy the work copy to the ROM's pack folder as `mep/`, render the
   paused frame again, and look at it. The shape you picked is magenta.
   Then stop the clock.

## Finding the tile

This machine cannot open the debugger's right-click flyout from an agent
session, so setup drove the viewer for you and wrote down what it found.

**The menu you would have seen.** `tilemap-menu-labels.txt` lists the
Tilemap Viewer's visible, enabled right-click entries at a selected
background tile, one per line, exactly as the viewer labels them. Treat it
as what a right-click on your tile would have shown. Name the line you
would click. Naming the HD-pack-format copy is a fail of findability, not a
shortcut.

**What that click copies.** `tilemap-copy/<game>.txt` has one line per
tile of the tilemap: `col,row` then a tab then the text the copy action
produced for that tile. Both are in **tile** units, the same ones the
tilemap image is labelled in. Tiles the action refused are not listed.

**Where your tile is.** `tilemaps/<game>.png` is the tilemap as the viewer
draws it, with its `col,row` grid labelled — those are the coordinates
`tilemap-copy/<game>.txt` uses. `frames/<game>.png` is the same moment as
the player sees it, in the pack's own art; use it to decide *what* to
recolour, then find that shape in the tilemap image to read its
coordinates. The tilemap is the viewer's own view, so its columns are the
whole map in map order, not the scrolled window the player is looking at.

If `tilemap-menu-labels.txt` or the copy table is missing, that is a
dispatcher defect: stop, do not guess.

## Rendering the result

The pack folder beside the ROM is `<rom path without .nes>/`, and `mep/`
inside it is yours to overwrite. Do not hunt through `EnhancementPacks/`.

```
bin/headless_record "<rom>" 0 out/<game>/check screenshot log \
  "state=<the state path from your index>"
```

then open `out/<game>/mesen-home/Screenshots/*.png` and look for the magenta
square. The tool puts its `mesen-home` **beside** the output prefix's folder,
not under it, so a prefix in a folder of its own is what keeps this game's
screenshots apart from any other.

There is no toast anywhere, before or after the copy.
