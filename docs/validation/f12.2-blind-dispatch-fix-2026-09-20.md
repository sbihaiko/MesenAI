# F12.2 — closing the two cold-read leaks found by the Sonnet sweep

**Date:** 2026-09-20
**Scope:** sweep tooling only (`scripts/f122_prepare_evaluator.py`'s
companions, `docs/validation/f12.2-sweep-evaluator-briefing.md`). No emulator
or MEP-pack code changed. This is not an ADR — it is a fix to a validation
protocol's dispatch mechanics, not an architecture decision.

The Sonnet sweep (`f12.2-sonnet-sweep-2026-09-19.md`) found that every
dispatched evaluator was contaminated on criterion 1 (findability) by two
leaks before it ever opened a sandbox file: a `gitStatus` system-reminder
naming the feature in a commit subject, and (for one evaluator) this
account's own persistent memory already documenting the feature's closure.
This note records what was tested, what turned out to be fixable from inside
a dispatch prompt and what did not, and what changed as a result.

## What was tested, empirically, on 2026-09-20

Three throwaway diagnostic subagents were dispatched (via the `Agent` tool,
no isolation flag, then again after changing the dispatching session's shell
`cwd`) and asked to report only what was already in their context before
calling any tool — no task content, purely introspective.

1. **A default dispatch reproduces the git leak exactly.** The subagent's
   `gitStatus` reminder named the same five recent commits as the
   dispatching session, including `feat(ui): Copy as MEP sheet cell puts a
   cell on the clipboard, unplaced` — the literal feature under test.
2. **A `cd` in the dispatching session's shell does not change what a
   subsequently-dispatched subagent sees.** After `cd`-ing the Bash tool's
   working directory to a plain, non-git `/tmp` folder and immediately
   dispatching another subagent, that subagent's reported primary working
   directory was still the dispatching session's original worktree, and its
   `gitStatus` reminder still carried the same five real commits. A subagent
   inherits the parent session's **fixed** primary directory, not whatever
   the parent's shell `cwd` happens to be at dispatch time. This rules out
   any per-call, prompt-side, or shell-side fix.
3. **The account's global `MEMORY.md` is injected regardless of cwd.** Both
   diagnostic subagents received the full memory file, including the
   `F12.2 fechado` bullet naming this exact feature and its closure PR — the
   second leak the Sonnet sweep found, reproduced independently of which
   directory the subagent's session was rooted in.

**Conclusion:** both leaks are structural properties of how this harness
dispatches subagents under this account, not something a briefing document
can suppress by asking the evaluator not to look. A prompt can only ask an
evaluator to behave honestly about a leak it cannot avoid seeing — it cannot
prevent the leak.

## What changed

**1. The briefing (`f12.2-sweep-evaluator-briefing.md`) now has an explicit
Contamination protocol.** Since the leaks can't be prevented from the
evaluator's side, the fix here is to convert a silent, unmeasured bias into
a logged, honest one: the evaluator is told outright that a `gitStatus`
reminder and its own memory reach it automatically and may already name the
feature; it must never run `git log`/`git show`/`git blame`/`git diff` (which
would only compound a leak it can't undo); it must never act on anything it
"already knows" from outside the sandbox; and it must log any such
contamination verbatim, then keep going through the rest of the protocol
mechanically. The results table's criterion 1 was updated to require "and
logged no contamination" explicitly, and the five-line end summary gained a
sixth, mandatory contamination line. This does not close the leak — nothing
inside a subagent dispatch can — but it stops a contaminated run from
silently scoring as a genuine find, which is what happened for 18 of 22 runs
in the Sonnet sweep (they saw the leak and self-reported it without being
asked to; the fix makes that reporting a required, structured part of the
protocol rather than something that depends on an evaluator noticing).

**2. `scripts/f122_make_blind_worktree.sh` — the actual fix for the git
leak, procedural rather than prompt-based.** Since a subagent's `gitStatus`
reminder always reflects the *dispatching session's own* primary directory
(point 2 above), the only way to close it is for the *coordinating session
itself* — not a subagent of it — to be rooted at a checkout whose recent
commit history does not name the feature under test. This script builds
that checkout: `git worktree add --detach`, then `checkout --orphan` and a
single squashed commit with a generic message ("chore: sandboxed evaluation
snapshot"), on a branch name that gives away nothing
(`blind-eval-snapshot-<timestamp>`). Tested directly on 2026-09-20: the
resulting worktree's `git log` shows exactly one commit, the generic one,
regardless of the real branch's history. **Using it requires opening a new
top-level Claude Code session with that worktree as its primary directory**
— a subagent dispatched from the current session would still inherit the
current session's real history, which is exactly why this couldn't be
verified end-to-end from inside this task (see *Honest limits*).

**3. `scripts/f122_redact_memory.py` — the fix for the memory leak.**
`MEMORY.md` is an account-level file, injected independent of cwd, so no
worktree trick touches it. This script comments out (never deletes) lines
matching caller-given patterns, with an automatic backup, and restores them
afterward. The intended use is: before opening the coordinating session for
a sweep, redact any MEMORY.md bullet that would name the feature under test;
run the sweep; `restore` immediately after. Tested on a scratch copy of a
MEMORY.md-shaped file on 2026-09-20: `redact` correctly comments out only
the matching line and leaves the rest of the file untouched; `restore`
recovers the original byte-for-byte from the backup.

## Verification

A throwaway evaluator was dispatched against a scratch copy of the 1942
sandbox (`/private/tmp/claude-503/f122-verify-sandbox`, built from the
existing `~/f12.2-opus-sandbox` game files) using the **new** briefing text,
to check the Contamination protocol produces the intended behavior rather
than to re-litigate whether the leak exists (already re-confirmed
structurally, above).

As expected, the leak reproduced — both the `gitStatus` reminder's commit
subject and the `MEMORY.md` "F12.2 fechado" bullet reached the evaluator
before it opened a single sandbox file (dispatching from inside this
session, the only option available to a task-scoped tool, unavoidably
inherits this session's real history and this account's real memory; see
*Honest limits*). What changed is what the evaluator *did* about it: it
quoted both leaks verbatim in its log, correctly marked criterion 1 void,
and then completed the rest of the protocol mechanically rather than either
silently coasting on the foreknowledge or aborting the run. It also caught
and correctly handled a third, sandbox-specific leak the briefing does not
yet name — the 1942 work copy still carried the finished cell from the real
2026-09-19 sweep (a pre-painted magenta cell at the exact tile a prior
evaluator had picked) — by deliberately picking a *different* tile so its
own run stayed an honest exercise rather than a copy of the answer sitting
in the sandbox. Build, lint, and the rendered screenshot all passed on the
supported path, `hires.txt` was never opened as a source, in ~16 of the
20-minute budget. This confirms the briefing change achieves its actual,
achievable goal — converting an unavoidable leak into a structured,
mandatory disclosure — without changing anything else about how the rest of
the protocol runs.

One follow-up worth carrying into the next sweep, found by this
verification run and not by either prior sweep: **sandbox work copies must
be freshly rebuilt per dispatch**, not reused across runs — a stale finished
cell from a previous evaluator is itself a criterion-1 leak (naming a
plausible answer to "which tile" if not "which action"), and this one
briefing addition doesn't cover it. `f122_prepare_evaluator.py` already
does a fresh `shutil.copytree(pack, work)` per invocation (see its
`main()`), so this is a reminder for whoever re-runs a sweep on an
already-populated `~/f12.2-*-sandbox/games/` directory by hand, not a code
defect.

## Honest limits

- **The git leak is not closed by anything in this repo alone.** The fix is
  procedural and depends on a human (or coordinating process) actually
  opening the *next* sweep's session rooted at a blind worktree, not on any
  code change an evaluator or a subagent dispatch can enforce on its own.
  This could not be verified end-to-end inside this task, because doing so
  requires a fresh **top-level** session, and every tool available here only
  dispatches subagents of the current one (which always inherit its real
  history, by design, per the empirical test above).
- **The memory leak's fix is similarly a discipline, not a guarantee** — a
  coordinator who forgets to run `redact` before a sweep gets the same leak
  as before. `f122_redact_memory.py` makes the redact/restore cycle cheap
  and reversible, not automatic.
- **`isolation: "remote"`** (a cloud sandbox environment) was considered as
  a structural alternative that might avoid both leaks at once — a remote
  environment plausibly has neither this local checkout's branch history nor
  this local account's `MEMORY.md` — but its availability is gated and this
  was not tested. Worth trying first on a future sweep before reaching for
  the worktree-squash procedure above.
- Criterion 1 remains fundamentally hard to score cleanly for *any* sweep
  dispatched from inside this harness under this account until a future
  coordinator actually uses the blind-worktree + memory-redact combination
  end to end; this task closes the mechanism gap, not the historical record
  of the two already-completed sweeps (both remain scored as contaminated on
  criterion 1, as their own docs already say).
