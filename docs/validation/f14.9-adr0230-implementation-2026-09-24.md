# F14.9 — ADR-0230 implemented: every drawn palette reaches a sheet (2026-09-24)

Slice F14.9 of `docs/roadmap/PRD-mesence-enhancement-ecosystem.md` (Phase 14),
implementing ADR-0230's Decision, including the item 2 refinement from the #448
review. User's decision and go-ahead, verbatim: *"aceito sua sugestão. pode
aplicar e rodar em paralelo"*.

## What shipped

- **Recorder (host-free).** `Core/NES/HdPacks/SheetColourways.h` classifies
  every drawn palette of a shape against the palette of the shape's cell.
  - The classification is `ClassifyPaletteRelation`, a port of
    `palette_folds.palette_relation` pinned by
    `docs/specs/golden/sheets/palette-relation-cases.txt`.
  - It decides exactness with `FoldIsExact`: on the render palette, one
    loader Brightness (`(int)(stof(text)*255)`, applied as
    `HdNesPack::AdjustBrightness` does) must rebuild every painted
    entry.
  - It plans the variant cells with `PlanPaletteCells` and lays them out with
    `InsertVariantCells`/`ApplyPaletteCells`.
  - It filters to the palettes `hires.txt` will carry with
    `WrittenPalettesByShape`.
- **How each drawn palette is handled.**
  - An exact fold goes into the sidecar tile entry's
    `"folds": [{"palette", "brightness"}]`.
  - Every other drawn palette gets a variant cell. That covers colourways
    and folds whose least-squares Brightness leaves a residual (the #448
    refinement).
  - A variant cell is rendered from the recorded art in that palette, carries
    `"variantOf": <base index>` and has no metatile.
  - Variant cells are inserted as whole rows directly beneath their base
    cell's grid row, in the base's column, so a cycle grid keeps its phase
    order.
  - A variant cell goes on the highest-ranked non-map sheet that holds a
    shape with the key.
- **`HdPackBuilder.cpp`.** `WriteSheetFiles` now queues each sheet, and
  `FlushSheetFiles` plans all of them and then writes them. A variant cell
  changes a sheet's size, and that is known only once every sheet exists.
- **`scripts/palette_folds.py`** is split out of `artist_chr_kit.py`.
  - `compute_folds` measures drift against the cell's palette. It no longer
    measures against the brightest step (item 3).
  - `entry_folds` validates a sidecar `folds` list, and
    `fold_brightness_text` matches the recorder's `"%.4f"`-trimmed text.
- **`mep_build`** emits one exact `defaultTile=N` rule per fold. The rule
  uses the cell's crop, the key source's rest fields and the fold's
  Brightness, painted or not.
- **`mep_lint`** (`lint_sheet_folds`) reports a malformed `folds` list as an
  error and a dangling `variantOf` as a warning.
- **`docs/remastering-a-game.md`** documents `folds` and variant cells.

## Method

- **Coverage.** A drawn key is an `N` rule in the recorder's `hires.txt`.
  It is covered when a sidecar entry names it as a cell key or as a fold.
  "Unobserved" counts sidecar keys that were never drawn.
- **Round trip.** `auto/textures` is copied to `textures/`, then built twice
  with `mep_build build`. The second `hires.txt` must be byte-identical to
  the first.
- **Render fidelity (keeps #447 out).** Every rule emitted for a drawn key is
  rendered and compared with the recording.
  - Built side: the rule's crop from the sheet PNG, which is
    `MesenSheets::Upscale`, nearest-neighbour. The rule's Brightness is
    applied as the loader does.
  - Recorded side: the same key's crop from the recording's
    `chr/Chr_*.orig.png` twin, also nearest-neighbour.
  - Neither side goes through xBRZ, so the pack-scale filter of #447 cannot
    enter the comparison.
  - Mismatches confined to the tile's colour-index-0 pixels are counted
    apart. Background sheets draw colour 0 opaque and sprite sheets draw it
    transparent, while a CHR page draws it by page type. This convention
    predates F14.9 and appears on base cells too.

Against the ADR's acceptance bound, which was "(c) folded", +61 / +76:

- **Colourway cells.** Castlevania adds 61, the bound exactly. Zelda adds 45,
  below its bound: measured against the cell (item 3), more of Zelda's steps
  are folds than under F14.4's brightest-first grouping.
- **Cells for residual folds**, stated apart as the refinement requires:
  - Castlevania: 6 cells.
  - Zelda: 82 cells, for 125 keys. These are Zelda's screen-fade steps. A
    residual key whose shape already has a cell on the same sheet shares
    that shape's variant stack, so there are fewer cells than keys.
- **Exact folds.** They add no cells. Every fold rule reproduces the recorded
  pixels, apart from the colour-0 convention above: 7, 2 and 2 rules, all on
  blank-tile cells.

**The one "other" mismatch.** It is on Castlevania: cell rule
`FF00000000000000FF00000000000000` / `FF23340F` on `sprites.png` against
`Chr_0.png`. It is a base cell rule, which F14.9 did not change.

**First run.** A run before the written-slot filter (next section) gave:

- Castlevania: 68 variant cells, 30 folds and 2 unobserved keys;
- Zelda: 127 variant cells and 143 folds.

The filter removed exactly the palettes that `hires.txt` never carried.

## Found on the way: AddTile slot collision

On CHR RAM, `AddTile` files a tile with `TileIndex >= 0` at
`paletteMap[palette][TileIndex % 256]`, so a later tile in the same slot
evicts the earlier variant. The evicted variant stays in
`_paletteVariantsByShape` but never gets a `<tile>` line. F14.9 counts a
palette as drawn only when its variant still holds a page slot
(`WrittenPalettesByShape`), so the sidecars never name a key the pack
lacks. Two such keys on Castlevania had shown up as "unobserved". The
eviction itself is pre-existing behaviour outside this slice.
